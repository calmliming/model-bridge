## 二、逐项差距分析与实现方案

### 1. 转发稳定性与协议兼容

#### GAP-02 [P0] Antigravity 非流式（`stream: false`）纳入 SSE 预读与畸形工具调用切换重试
- **sub2api 参考**：
  - `14a5fe305` (`backend/internal/pkg/antigravity/response_transformer.go`, `backend/internal/service/antigravity_gateway_compat.go`)
  - `c591412c4` (`backend/internal/service/antigravity_gateway_service.go`)
- **model-bridge 现状**：
  1. 在 `src/routes/relay.ts:2436`（`relayAntigravityMessages`）、`2475`（`relayAntigravityChat`）、`2514`（`relayAntigravityResponses`）中，调用 `executeWithFailover` 时传入的是 `stream ? peekAntigravityStreamStart : undefined`。
  2. 然而 Antigravity 上游接口固定为 `v1internal:streamGenerateContent?alt=sse`（无论下游请求 `stream` 是 `true` 还是 `false`，上游返回的始终是 SSE 流）。
  3. 当客户端以非流式（`stream: false`）请求时，`executeWithFailover` 跳过 `peekAntigravityStreamStart`，只要上游 HTTP 状态码为 `200` 就视为账号成功并退出故障切换循环；随后在 `toMessagesResponse` / `toChatCompletionResponse` / `toResponsesObject`（`src/routes/relay.ts:3695-3728`）中才解析 SSE 帧，一旦遇到 `MALFORMED_FUNCTION_CALL`、空候选或流内错误帧，直接向客户端抛 `502`，**丧失了同号重试与跨号切换能力**。
  4. 此外，在 `antigravityStreamStartVerdict`（`src/providers/antigravity/response.ts:190-206`）中，第 199 行仅检查 `Object.keys(part).some((key) => key !== 'thought' && key !== 'thoughtSignature')`，若首个 `part` 为畸形的 `functionCall`（例如 `name` 非字符串或 `args` 非对象，且 `finishReason` 尚未置为 `MALFORMED_FUNCTION_CALL`），会被误判为 `'pass'` 放行，随后在 `parseAntigravityEvents`（第 72 行）中才触发 `failed = true` 导致半截断流。
- **影响**：
  - 非流式调用 Antigravity（Claude/Gemini 模型）遇到上游偶发 `MALFORMED_FUNCTION_CALL` 或空包时直接向客户端报 502，无法自动重试或切换备用账号。
  - 流式首包带结构畸形的 `functionCall` 时会提前向客户端刷出响应头，无法无感重试。
- **建议改法**：
  1. 在 `src/routes/relay.ts:2436, 2475, 2514` 三处将 `stream ? peekAntigravityStreamStart : undefined` 改为始终传入 `peekAntigravityStreamStart`（因为上游恒为 SSE）。
  2. 在 `src/providers/antigravity/response.ts:190-206` 的 `antigravityStreamStartVerdict` 中，若 `part` 含 `functionCall`，校验 `typeof part.functionCall?.name === 'string' && part.functionCall.name.length > 0 && object(part.functionCall?.args)`；不合法时直接返回 `{ kind: 'retry', reason: 'malformed_function_call' }`。
- **工作量 / 风险 / 优先级**：`S` / `低` / **P0**

#### GAP-03 [P1] OpenAI / 兼容上游非流式返回无 `Content-Type: text/event-stream` 的 SSE 响应体自动识别与转换
- **sub2api 参考**：
  - `4db8402b5` (`backend/internal/service/openai_gateway_passthrough.go:2323-2328`)
- **model-bridge 现状**：
  - 在 `src/routes/relay.ts:1518`（`sendBuffered`）、`1533`（`sendResponsesAsChat`）、`2770`、`2941`、`3350` 等处，判断是否将上游响应按 SSE 解析合并为 JSON 严格依赖 `upstream.headers.get('content-type')?.includes('text/event-stream')`。
  - ChatGPT OAuth Codex 后端以及部分兼容中转网关在偶发情况下会返回标准 SSE 帧（以 `event:` 或 `data:` 开头），但遗漏 `Content-Type` 响应头或返回 `text/plain` / `application/octet-stream`。
- **影响**：
  - 非流式请求收到无 `Content-Type: text/event-stream` 的 SSE 文本时，`sendBuffered` 会将其作为普通文本原样返回给预期 JSON 的客户端，且 `parseUsage(JSON.parse(raw))` 解析失败导致該次请求记账 Token 为 0。
- **建议改法**：
  - 在 `src/routes/relay.ts` 新增辅助函数 `bodyHasSseFraming(raw: string): boolean`（去除前导空白后匹配 `/^(?:event:\s*\S+|data:\s*\{)/m`），在 `sendBuffered` 和非流式转换分支中将判定条件升级为 `isEventStreamContentType(upstream.headers) || bodyHasSseFraming(raw)`。
- **工作量 / 风险 / 优先级**：`S` / `低` / **P1**

#### GAP-04 [P1] 流式中途客户端断开（`client_disconnected`）后的尾包 Usage 静默排空与计费防漏记
- **sub2api 参考**：
  - `94c7d6b02` (`backend/internal/service/openai_gateway_service.go`, `claude_gateway_service.go` — 流式客户端断开后继续读取上游以合并最终 usage)
  - `2b1f12938` (`backend/internal/service/gateway_service.go` — 客户端取消的流式请求同样记录 token 用量与费用)
- **model-bridge 现状**：
  - `src/routes/relay.ts:2216-2222` 注册了 `reply.raw.once('close', abortOnClose)`，一旦客户端在收到最后一个文本 delta 后立即关闭连接（许多 CLI/脚本工具在收到结束标记或满足停止词后立刻掐断 socket），`controller.abort('client_disconnected')` 会立即中止上游 `fetch` 流。
  - 对于仅在流尾（如 `message_delta`、`response.completed` 或最后一个 `data: {...,"usage":...}` chunk）才下发 `output_tokens` 的上游，立即 abort 上游会导致尾包 `usage` 丢失，最终落入 `recordCancelledStreamUsage` 时 `outputTokens` 偏少甚至为 0。
- **影响**：
  - 客户端如果在收到正文末尾的瞬间主动断开连接，可能绕过尾包 `usage` 统计，造成输出 Token 漏计费。
- **建议改法**：
  - 当流已经进入响应体传输阶段（`firstTokenMs !== null`）且客户端断开时，不立即 `abort` 上游 `fetch`，而是标记下游 writer 为 `detached`（停止向 `reply.raw` 写入），并为上游流挂载一个短排空超时（例如 `3000ms`），尝试读完剩余尾帧以提取完整 `usage`，若超时仍未结束再 `controller.abort('client_disconnected')` 并以已累积的 parser 结果入账。
- **工作量 / 风险 / 优先级**：`M` / `中` / **P1**

### 3. 账号调度与限流

#### GAP-07 [P1] 国产 Coding Plan（智谱 GLM / Kimi / Qwen / MiniMax / 小米）区分「瞬时频率 429」与「额度耗尽 429」
- **sub2api 参考**：
  - `de908ed6d` (`backend/internal/service/ratelimit_cn_providers.go:124-206, 375-390` — 区分频率型 429 与滚动窗口额度耗尽 429)
  - `1774b79dc` (`backend/internal/service/ratelimit_cn_providers.go` — Coding Plan 额度感知调度与 429 分类)
- **model-bridge 现状**：
  - 在 `src/routes/relay.ts:1206-1239`（`classifyUpstreamFailure`）中，除 OpenAI / Claude 以外的所有 Provider 在返回 HTTP `429` 时一律返回 `{ penalty: 'rate_limited', retryable: true, accountScoped: true }`。
  - 当国产模型上游（如智谱 GLM 返回 `{"error":{"message":"您的账户已达到速率限制，请您控制请求频率"}}`）未携带 `Retry-After` 响应头时，`penalizeAccount`（`src/accounts/scheduler.ts:196`）会按默认 `COOLDOWN_MS.rate_limited = 10 * 60_000` 将该账号**直接冷却停调 10 分钟**！
  - 反之，若国产 Coding Plan 返回的是「余额不足 / 套餐额度已用尽」，目前也仅冷却 10 分钟，缺少更长冷却或明確区分。
- **影响**：
  - 智谱 GLM、Kimi、Qwen、MiniMax 等账号在遇到瞬时并发限频（QPS/RPM 触发的 429，几秒后即可恢复）时，会被误判停调长达 10 分钟，严重降低账号池可用率。
- **建议改法**：
  1. 在 `src/routes/relay.ts`（或独立的 `src/providers/cnRateLimit.ts`）中新增针对 `zhipu` / `kimi` / `qwen` / `minimax` / `xiaomi` / `deepseek` 的 429 响应体分类函数：
     - **频率型 429**（命中 `速率限制`、`请求频率`、`访问频率`、`请求过于频繁`、`rate limit exceeded`、`too many requests`，且**不含** `额度`、`已用尽`、`用完`、`insufficient`、`balance`、`quota`）：使用短冷却（例如 `5_000ms`～`15_000ms`），快速恢复调度。
     - **余额/套餐耗尽型 429/402**（命中 `余额不足`、`额度已用尽`、`套餐额度`、`insufficient_balance`）：使用长冷却（如 `30 * 60_000ms` 或对齐窗口重置时间）并记录明确原因。
- **工作量 / 风险 / 优先级**：`M` / `低` / **P1**

- **建议改法**：
  1. 在 `src/usage/pricing.ts` 新增 `OPENAI_GPT6_1_TERRA` 与 `OPENAI_GPT6_1_TERRA_PRIORITY` 定价常量，并在 `PRICING_TABLE` 及长上下文阶梯匹配（`>272k`）中注册 `gpt-6.1-terra`。
