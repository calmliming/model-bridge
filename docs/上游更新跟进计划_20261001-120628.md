## 三、实施细则

### 1. Anthropic 流式用量取 `message_delta` 累计值（P1，计费缺陷）

**问题**：[`src/providers/claude/usage.ts`](../src/providers/claude/usage.ts) 的 `createStreamParser` 只从 `message_start` 读取输入和缓存，`message_delta` 只更新输出。Sub2API 把 GPT 等非 Anthropic 账号转换成 Anthropic 流时，`message_start` 的 `input_tokens` 固定为 0，真实的输入和缓存数只放在最后的 `message_delta` 里（上游 `backend/internal/pkg/apicompat/responses_to_anthropic.go` 第 283–291、338–339 行）。

**复现**：向本地解析器依次输入 `message_start{input_tokens:0}` 和 `message_delta{input_tokens:1200, cache_read_input_tokens:3000, output_tokens:80}`，结果为 `inputTokens:0, cacheReadTokens:0, outputTokens:80`，输入和缓存全部漏记。

**影响范围**：`claude`、`claude-chat`、`sub2api` 三个路由的流式请求共用这个解析器（[`src/routes/relay.ts`](../src/routes/relay.ts) 第 271、287、664 行）。官方 Anthropic 的 `message_start` 已包含输入数，通常不受影响；实际漏记集中在 **Sub2API Messages 入口转发到非 Claude 账号**的流式请求。缓冲模式的 `claudeSseToChatCompletion` 已合并 `message_delta.usage`，不受影响。

**改动**：

- [x] `message_delta.usage` 中出现的 `input_tokens`、`cache_creation_input_tokens`、`cache_read_input_tokens` 覆盖 `message_start` 的同名字段。Anthropic 规定 `message_delta` 的用量是累计值，覆盖也能让官方流在服务端工具等场景下更准确。
- [x] 某个字段缺失时保留之前的值；**不要**根据后到的缓存字段去推算并扣减 `input_tokens`。上游 [0416c9e](https://github.com/Wei-Shaw/sub2api/commit/0416c9ede47e8fbab4a705dc3eeb8b21bf928d73) 已撤回这类推断，因为不同供应商对 `input_tokens` 是否含缓存的约定不一致。
- [x] 若输出数在流中为 0 但 `message_delta` 有值，保持现有“最后一个为准”的行为。

**验收**：

- 单元测试覆盖：官方流（start 有值、delta 只有输出）结果不变；Sub2API 转换流（start 为 0、delta 有全量）记全；delta 只带缓存字段时不扣减输入；多个 delta 时取最后一个。
- `relay.integration.test.ts` 用模拟上游走 `sub2api` 路由，确认 `recordUsage` 的输入、缓存与费用正确。

**历史影响评估**（只读查询，上线前在生产库执行一次即可）：

```sql
SELECT date_trunc('day', to_timestamp(ts / 1000)) AS day,
       count(*) AS rows, sum(output_tokens) AS output_tokens
FROM usage_logs
WHERE provider = 'sub2api' AND status = 'success'
  AND input_tokens = 0 AND cache_read_tokens = 0 AND output_tokens > 0
GROUP BY 1 ORDER BY 1 DESC;
```

是否补收历史费用属于业务决定，本计划不做自动补扣。

**改动**：

### 7. Antigravity 空流换号重试（P2）

**问题**：上游空响应时只返回 `thoughtSignature`，以 `MALFORMED_FUNCTION_CALL` 结束。本地 [`src/providers/antigravity/response.ts`](../src/providers/antigravity/response.ts) 第 101–116 行会把它识别为失败并返回错误事件，但这时响应头已经发出，无法换账号重试。

**设计要点**：

- [x] 流式响应在首个有效内容（文本、思考、工具调用；不包括只有签名的事件）到达前先不发送响应头，期间发送 SSE 注释心跳保活（Google GenAI SDK 客户端仍按现有规则关闭心跳）。
- [x] 在有效内容前遇到 `MALFORMED_FUNCTION_CALL` 或空流时，把本次尝试记为失败并换下一个账号，计入 `attemptCount`。
- [x] 设置首包等待上限，超时后按现有错误路径处理；不影响其他提供方。

这一项会改动通用流式路径，建议单独提交，并补充首包超时与客户端取消的集成测试。

### 8. 余额模式在途预占（P2，业务取舍）

**现状**：[`src/middleware/apiKeyAuth.ts`](../src/middleware/apiKeyAuth.ts) 在余额大于 0 时放行；[`src/wallet/manager.ts`](../src/wallet/manager.ts) 结算时允许欠费，之后的请求会被拦截。并发的高成本请求可以造成一次性透支，透支上限受用户并发数限制约束。

**可选方案**（v0.2.11 默认开启，并列为破坏性变更）：

- [x] 准入时按 `max_tokens` 和模型价格估算成本，原子性地预占在途额度；结算后释放，按实际费用扣款；预占过期后自动释放、不续期。
- [x] 设置开关，默认关闭以保持现有行为；余额较低的用户开启后会更早被拒绝。

开放充值后如果出现欠费回收问题，再提升优先级。

### 9. API Key 创建数量与频率限制（P2）

本地已开放邮箱注册和在线充值，但没有 Key 创建限制。建议参考上游默认值：每用户最多 200 个有效 Key、每小时最多创建 60 次，可配置，0 表示不限制。只限制用户端，管理员不受限。

### 10–13. 运营与体验（P3）

- **Claude 原生限额重置**：上游使用 `GET https://api.anthropic.com/api/oauth/usage?cedar_ember=1&skip_spend=1` 读取 grants 和 `next_grant_id`，通过 `/api/oauth/profile` 获取组织，再调用 `POST /api/organizations/{org}/reset_rate_limits` 兑换。这些是非公开接口，需要幂等键、组织级防重入（结果不明时锁定 24 小时）、二次确认，并且不能把 grant 或组织 ID 返回给前端。可以沿用本地 OpenAI 重置的界面和接口形态。
- **Codex 远程模型目录**：需要先提供面向客户端的 Codex 模型清单接口，再在 Key 弹窗中生成 `model_catalog_json` 配置（Codex 0.156.0+）。依赖动态模型目录的进展。
- **消息项补 `type: "message"`**：上游是为了兼容 StepFun 这类严格上游，Codex 后端不需要。改动很小，可以和第 5 项一起做。
- **ChatGPT 套餐标签**：只是前端显示，按需更新映射。
