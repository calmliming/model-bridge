# 生成服务账号不可用原因说明

## 现象

调用 GrsAI 图片生成时报：

```
Model Bridge 503: no 生成服务 account configured
```

原文是 `no grsai account configured`，出站前经 `publicMediaError` 把渠道名 `grsai` 替换成「生成服务」（`src/providers/publicIdentity.ts`）。该文案由 `src/routes/relay.ts` 在「没有选中任何账号」时生成。

## 排查结论：账号存在，只是处于冷却

数据库中 GrsAI 账号为 `provider=grsai`、`status` 正常、无分组归属，调度查询能命中；直接调用 `pickAccount('grsai', [], null, null, 'gpt-image-2')` 返回该账号。因此报错不是「没配置账号」，而是**报错当下账号不可调度**。

用真实 API Key 对运行中的服务复现，得到完整因果链：

1. 第一次 `POST /v1/images/generations`：账号被选中并真的调到了上游，上游返回 `502 excessive system load`（GrsAI 生成队列过载），下游按分类结果把账号标记为 `error`，冷却 2 分钟（5xx 统一按 `penalty: 'error'` 处理）。
2. 同一个请求的第二次尝试：账号刚被标记、且已进入 `tried` 排除列表，`pickAccount` 返回 null。
3. 紧接着的第二次请求：账号仍在冷却窗口内，`pickAccount` 再次返回 null，于是报出 `no grsai account configured`。
4. 冷却到期后异步任务 `POST /v1/api/generate` 提交成功并最终 `succeeded`，证明渠道与账号本身没有问题。

也就是说：**一次上游瞬时过载，会让后续约 2 分钟内的所有图片请求都收到「没有配置账号」这种误导性提示**，而账号其实一直在，配置也一直是对的。

## 本次改动

只修「说法与事实不符」，不动调度与计费策略：

1. `src/accounts/scheduler.ts` 新增 `accountAvailability()`：在 `pickAccount` 返回空之后，按 `total / active / cooling / disabled` 给账号池分桶，并给出最早的冷却到期时间。必须在 `pickAccount` 之后调用，因为过期冷却是在那一步释放的。
2. 新增 `unavailableAccountMessage()`，按事实选择文案：
   - 池里确实没有账号 → `no 生成服务 account configured`
   - 全部被禁用 → `all 生成服务 accounts are disabled`
   - 账号都在冷却 → `生成服务账号正在冷却中（共 1 个，最快约 42 秒后恢复），请稍后重试`
   - 本请求已试过账号但仍无可用 → `all 生成服务 accounts are unavailable`
3. `src/providers/publicIdentity.ts` 新增 `publicProviderLabel()`：给对外文案提供渠道中文名（`grsai` → `生成服务`，`claude` → `Claude` 等），未知渠道回退为原 id，保证以后新增渠道时文案仍然可读。该中文名不会被 `publicMediaError` 的反向替换影响。
4. `src/routes/relay.ts`（图片/对话等所有中转请求）与 `src/routes/media.ts`（`/v1/api/generate`、`/v1/videos` 异步提交）都改用上述诊断文案，异步提交路径同时把提示改为按原因输出。

## 未改动（需要决策）

上游 5xx（含 GrsAI 的 `excessive system load`）目前统一按 `penalty: 'error'` 让账号冷却 2 分钟（`src/routes/relay.ts` 的 `classifyUpstreamFailure` + `applyFailureSideEffects`）。对只有单个账号的渠道，这等于「上游抖一下，本渠道停两分钟」。没有顺手改的原因：

- 5xx 里既有「稍等即好」（生成队列过载）也有「真挂了」，缩短冷却会让故障期间的重试更频繁地打到上游；
- 这个策略同时作用于所有渠道，属于全局行为，不适合夹在文案修复里一起改。

可选方案：对「上游服务过载」这一类信号（响应体含 `load` / `busy` / `overloaded` / `capacity`）单独给较短冷却（如 30 秒），或干脆不惩罚账号、只在响应里告知可重试。

## 验证

- 新增 `unavailableAccountMessage` 的 6 项单测（含复现本次 bug 的用例：冷却中的账号不得再被判为「未配置」）与 `publicProviderLabel` 的 1 项单测。
- 实测：临时把账号置为冷却后，两个入口都返回 `503 {"error":"生成服务账号正在冷却中（共 1 个，最快约 39 秒后恢复），请稍后重试"}`；恢复账号后图片生成正常。
- 全量回归 123 个测试文件通过、1302 → 1309 项测试通过；`tsc --noEmit` 通过。
