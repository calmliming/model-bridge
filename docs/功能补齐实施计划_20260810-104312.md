## 0. 阅读前须知

### 0.1 本仓库的既有约定（实施时必须遵守）

| 事项 | 约定 |
|---|---|
| 数据库变更 | **同时**改 `src/db/schema.ts`（Drizzle 类型）和 `src/db/init.ts`（启动期建表/加列）。加列一律用 `ALTER TABLE ... ADD COLUMN IF NOT EXISTS`，保证幂等、可重复启动。不使用独立 migration 步骤。 |
| 设置项 | 走 `settings` 键值表，在 `src/db/settings.ts` 里补一对 `getXxx` / `setXxx`，参考已有的 `quota_autopause_percent`、`openai_scheduling_strategy` 写法。 |
| 出站请求 | 一律经 `src/http/upstream.ts` 的 `fetchWithConnectTimeout`，不要直接裸 `fetch` 上游。 |
| 测试 | 新增逻辑必须带 `vitest` 单测，与被测文件同目录 `*.test.ts`。提交前跑 `npm test` 与 `npm run typecheck`。 |
| 提交信息 | 中文书写，按 `1. 2. 3. …` 编号说明改动内容与原因。 |
| 文档 | 新增说明文档放 `docs/`，命名 `中文名称_YYYYMMDD-HHmmss.md`。 |

### 0.2 排序原则

1. **安全在前** —— 已存在真实攻击面的先修，避免边加功能边扩大暴露面。
2. **地基合并** —— 多个功能共用的数据库列 / 中间件 / 表，合并成一次改动，避免反复迁移。
3. **风险递增** —— 不动调度主路径的在前，改调度与计费的在后。
4. **可独立交付** —— 每一项都能单独上线并回滚，不做跨阶段的大爆炸式重构。

## 阶段一 · 安全加固（P0，先做）

> 目标：把「已经存在但未防护」的攻击面补上。这一阶段不新增业务能力，全部是防御性改动，做完再动功能。

### 1.1 出站 URL allowlist / SSRF 防护 ★最高优先

**状态：✅ 已实现（2026-08-13）**

**为什么排第一**：本仓库存在**管理员可控的服务端出站地址**，且已被当作正常功能使用——
- `accounts.proxy_url`（[schema.ts:18](../src/db/schema.ts#L18)）在 sub2api 上游场景中被当作**自定义 Base URL** 写入（见 [admin.ts:1142](../src/routes/admin.ts#L1142)、[admin.ts:1239](../src/routes/admin.ts#L1239)），并直接传给 `relaySub2ApiMessages` / `relaySub2ApiChatCompletions` / `relaySub2ApiResponses`（[relay.ts:556](../src/routes/relay.ts#L556)、[:568](../src/routes/relay.ts#L568)、[:581](../src/routes/relay.ts#L581)）。
- 目前 `src/accounts/manager.ts:110` 只做了 `trim()` 和去尾斜杠，**没有任何协议、主机、私网校验**。
- sub2api 在 v0.1.169 刚修复同类问题（GHSA-vrxq-qm4h-6hgg，影响其 v0.1.135–v0.1.168）。

**实现要点**
1. 新建 `src/http/urlGuard.ts`：
   - `assertSafeUpstreamUrl(raw: string): URL` —— 校验协议仅 `http:` / `https:`；拒绝含凭据（`user:pass@`）的 URL；拒绝非常规端口（可配置白名单）；**拒绝路径穿越片段**（`..`、编码后的 `%2e%2e`）。
   - `resolveAndAssertPublicHost(url: URL): Promise<void>` —— DNS 解析后逐个校验 A/AAAA 记录，拒绝回环、RFC1918、链路本地 `169.254.0.0/16`（含云元数据 `169.254.169.254`）、IPv6 ULA `fc00::/7` 与 `::1`。
   - 提供全局开关 `UPSTREAM_URL_GUARD_ENABLED`（默认 `true`）与显式放行列表 `UPSTREAM_HOST_ALLOWLIST`（逗号分隔），供自建内网上游的用户豁免。
2. **写入时校验**：`src/accounts/manager.ts` 的 `createAccount` / `updateAccount` 在保存 `proxyUrl` 前调用 `assertSafeUpstreamUrl`，非法直接 400 报错给管理端。
3. **出站时校验**（防 DNS rebinding 与历史脏数据）：在 `src/http/upstream.ts` 的 `fetchWithConnectTimeout` 入口做一次 `resolveAndAssertPublicHost`，命中即抛错，走现有 failover。
4. 官方上游域名（`api.anthropic.com`、`chatgpt.com` 等）走内建 allowlist 直接放行，不做 DNS 二次解析，避免热路径开销。

**数据库变更**：无。

**验收标准**
- 单测覆盖：`http://127.0.0.1:8080`、`http://[::1]/`、`http://169.254.169.254/latest/meta-data/`、`https://evil.com/../../admin`、`file:///etc/passwd`、带凭据 URL —— 全部被拒。
- 正常 sub2api 上游地址（公网域名）保存与转发不受影响。
- 关闭开关后行为回退到当前状态（保证存量私网部署可平滑升级）。

**风险**：存量用户可能已把 `proxy_url` 指向内网自建网关。**升级说明必须写明**：升级后此类账号会失效，需把主机加入 `UPSTREAM_HOST_ALLOWLIST`。启动时扫描一遍存量 `proxy_url`，命中私网的打 WARN 日志列出账号 ID。

### 1.2 面板 API 限流

**状态：✅ 已实现（2026-08-13）**

**现状**：`src/middleware/limits.ts` 只覆盖 relay 的 per-API-key 限流与并发门；`src/auth/security.ts:54` 的 `checkLoginRateLimit` 只覆盖登录。**其余全部管理端 / 用户端接口无限流**，包括 `POST /api/auth/register`（[auth.ts:95](../src/routes/auth.ts#L95)）——开放注册打开后可被批量刷号。对应 sub2api v0.1.166。

**实现要点**
1. 在 `src/middleware/limits.ts` 复用现有的可插拔（内存 / Redis）滑动窗口，抽出通用 `checkWindowLimit(key, limit, windowMs)`。
2. 新增 `src/middleware/panelRateLimit.ts`，提供 Fastify `onRequest` 钩子：
   - **已认证接口**：按 `userId` / `adminId` 维度限流（默认 300 req/min）。
   - **公开接口**（`/api/auth/*`）：按 `request.ip` 维度限流（默认 60 req/min），IP 取值直接复用已有的 [trustProxy.ts](../src/http/trustProxy.ts)，无需重复处理 `X-Forwarded-For`。
   - **写操作**（register / invite accept / 兑换码）单独收紧（默认 10 req/min）。
3. 注册到 `src/routes/{admin,auth,users,usage}.ts`，**不挂到 relay 路由**（relay 已有 per-key 限流，避免双重计费式限流）。
4. 超限返回 429 + `Retry-After`。Redis 不可达时沿用现有 fail-open 策略。

**数据库变更**：无。限流阈值以环境变量 + `settings` 表双通道配置。

**验收标准**：单测覆盖窗口滚动与多维度隔离；手工验证连续打 `/api/auth/register` 触发 429 且不影响正常登录。

### 1.3 2FA / TOTP

**现状**：全仓无 `totp` / `otpauth` / `webauthn` 任何实现，管理员登录仅密码 + 可选 Turnstile。

**实现要点**
1. 依赖：`otplib`（或自行实现 RFC 6238，约 60 行，避免新增依赖——**倾向自实现**，与仓库「轻量」定位一致）。密钥用现有 `src/crypto.ts` 的加密函数落库。
2. 数据库：
   - `users` 加 `totp_secret_encrypted TEXT`、`totp_enabled BOOLEAN NOT NULL DEFAULT FALSE`、`totp_recovery_codes JSONB`（哈希后的一次性恢复码）。
   - 管理员账号存于 `settings` 表（见 `src/auth/admin.ts`），对应加 `admin_totp_secret` / `admin_totp_enabled` 两个 setting 键。
3. 流程：
   - **绑定**：`POST /api/admin/2fa/setup` 返回 `otpauth://` URI + 二维码数据（前端用现成库渲染）→ `POST /api/admin/2fa/confirm` 校验一次动态码后才真正启用，避免绑错锁死。
   - **登录**：密码校验通过后，若 `totp_enabled` 则返回 `{ requires2fa: true, challengeToken }`（短期 JWT，5 分钟），前端二次提交动态码换正式 token。
   - **恢复码**：启用时一次性生成 10 个，仅展示一次，使用即作废。
   - **解绑**：需同时提供密码 + 当前动态码。
4. 防爆破：动态码校验并入 1.2 的限流（同一账号 5 次/分钟），并允许 ±1 时间窗容差。

**验收标准**：单测覆盖 TOTP 生成/校验/时间窗容差/恢复码一次性；绑定未确认时不影响原登录；关掉 2FA 后旧流程完全不变。

**用户可见变更**：设置页新增「两步验证」卡片（管理端与用户端各一处）。

### 1.4 Passkey 免密登录

**说明**：排在 1.3 之后，因为共用「二次验证挑战」这套前后端流程，TOTP 先落地可复用其 challenge 机制。对应 sub2api v0.1.168。

**实现要点**
1. 依赖 `@simplewebauthn/server` + `@simplewebauthn/browser`（WebAuthn 协议自实现不划算，这里接受新增依赖）。
2. 数据库：新增 `user_credentials` 表 —— `id` / `user_id` / `credential_id`(unique) / `public_key` / `counter` / `transports` / `name` / `created_at` / `last_used_at`。
3. 接口：`/api/auth/passkey/register-options`、`/register-verify`、`/login-options`、`/login-verify`，以及撤销接口。
4. **注册与撤销均需先验证密码**（对齐 sub2api 做法），防止会话被劫持后静默加凭据。
5. `rpID` 从请求 Host 推导，需在文档中提示反代场景必须配置正确的 `PUBLIC_ORIGIN`。

**验收标准**：Chrome / Safari 各验证一次注册 + 登录；撤销后无法再登录；未配置 HTTPS 的本地开发走 `localhost` 例外。

### 1.5 流式计费失败熔断

**现状**：非流式已做 fail-closed（见对比文档第 2 项），流式路径仍缺。sub2api v0.1.170/171 修过多起「流式中断丢用量导致漏计费」「计费失败丢用量记录」。

**实现要点**
1. 审计 `src/routes/relay.ts` 的 `sendStreaming` 全路径：上游中断、客户端断开、`recordUsage` 抛错三种情况下，是否都有兜底落库。
2. `src/usage/recorder.ts` 的 `recordUsage` 返回 `boolean`（已有），失败时：
   - 写入本地降级队列（内存 ring buffer + 落盘 JSONL），后台任务重试；
   - 连续失败超阈值触发**熔断**：新请求直接 503 并打 ERROR 日志，而不是继续放行免费流量。
3. 熔断状态通过 `settings` 暴露给管理端总览页，可手工复位。
4. 与已有的 `waitForPendingUsage()`（[recorder.ts:124](../src/usage/recorder.ts#L124)）优雅关停逻辑对齐，确保熔断队列在 `SIGTERM` 时也被排空。

**验收标准**：单测模拟 DB 写入失败，验证降级队列接管、重试成功后补记、连续失败触发熔断；关停时队列不丢。

### 2.3 上游响应模型审计

**状态：✅ 首期 `log` 模式已实现（2026-08-13）**

**为什么对本项目价值更高**：本仓库已把 sub2api 自身作为上游接入（`src/providers/sub2api/`，`/api/sub2api/v1/*`），**上游是否老实返回所请求的模型无法验证**。这项能力在 sub2api 那边是 v0.1.172 新增，在这里是刚需。

**实现要点**
1. 各 provider 的 usage 提取处（`src/providers/*/usage.ts`、`responses-usage.ts`）已在解析上游响应，顺带提取响应体 / SSE 事件里的 `model` 字段，回填到 `UsageRecord.upstreamModel`。
2. 归一化后比较：忽略大小写、忽略已知别名映射（复用 `src/keys/modelMapping.ts` 的映射结果作为期望值——**比较对象应是映射后的模型，而不是客户端原始请求模型**），不一致则置 `model_mismatch = true`。
3. 管理端用量列表加「仅看模型不一致」筛选与醒目标记；总览页加不一致计数。
4. 可选增强：设置项 `model_mismatch_action`，取值 `log`（默认）/ `penalize`（不一致时给该账号降权或冷却）。首期只做 `log`，避免误判影响调度。

**验收标准**：单测覆盖别名归一化（如请求 `deepseek-chat` → 映射为 `deepseek-v4-flash` → 上游返回 `deepseek-v4-flash` 判定为一致）；构造上游返回不同模型的 mock，验证标记正确。

### 2.4 操作审计日志

**现状**：全仓无 audit 表或中间件。管理员改设置、调账、发兑换码、改账号，全部无留痕。多人共管或事后追责时是硬伤。

**实现要点**
1. 新表 `audit_logs`：`id` / `actor_type`(admin|user|system) / `actor_id` / `action` / `target_type` / `target_id` / `summary` / `detail JSONB` / `ip` / `user_agent` / `created_at`。加索引 `(created_at DESC)` 与 `(actor_id, created_at DESC)`。
2. 新建 `src/audit/recorder.ts`，提供 `recordAudit(entry)`，**异步写入且失败不阻断主流程**（与计费不同，审计失败只打日志）。
3. 埋点范围（先覆盖高价值写操作，不做全量）：
   - 设置变更（`PATCH /api/admin/settings`）—— **记录变更前后值，敏感字段只记「已变更」不记明文**
   - 账号增删改、OAuth 完成、账号启用/禁用
   - API Key 增删改、配额调整
   - 钱包调账、兑换码生成、订阅授予/撤销
   - 用户禁用/启用、2FA 解绑、Passkey 撤销
   - 系统更新触发
4. 管理端新增「审计日志」页，支持按操作者 / 动作 / 时间范围筛选。
5. 保留期：设置项 `audit_retention_days`（默认 180），由现有 `src/jobs/` 下的后台任务清理。

**验收标准**：改一次设置、调一次账、删一个 Key，三条审计记录字段完整；密钥类字段确认不落明文。

**实现要点**
1. 新建 `src/accounts/channelMetrics.ts`：以 `usage_logs` 为唯一数据源，按 `(account_id, provider, model, 时间桶)` 聚合成功率、P50/P95 延迟、首 Token 延迟（`first_token_ms` 已有）、错误码分布、限流次数。

3. 管理端「渠道监控」页：

4. `health.ts` 的主动探活**保留但降级**为「手工触发的连通性测试」（配合已有 `src/accounts/tester.ts`），不再作为调度输入的自动打分来源；调度侧改读被动指标。

**风险**：调度输入源切换需谨慎。首期**只做展示，不接调度**；确认指标稳定后再单独提一次 PR 把 `scheduler.ts` 的健康分切到被动指标。

## 阶段三 · 调度与计费精度（P2）

> 目标：提升计费准确性与分组表达能力。**本阶段直接改调度主路径，每一项都必须单独上线并观察一段时间。**

### 3.1 Codex 客户端版本自动同步（**先做，独立小项**）

**现状**：[src/providers/openai/constants.ts](../src/providers/openai/constants.ts) 硬编码 `codex_cli_rs/0.20.0`。对比文档里 `gpt-5.6-luna 404`「待验证」项大概率就是上游按 UA 版本 gate 导致。sub2api v0.1.171 已做每 6 小时自动同步官方稳定版。

**实现要点**
1. 新增后台任务 `src/jobs/codexVersionSync.ts`：每 6 小时拉取 Codex CLI 官方稳定版本号，写入 `settings.codex_client_version`。
2. `constants.ts` 的 `CODEX_USER_AGENT` 改为运行时从 settings 读取（带内建默认值兜底），四个引用点（relay / quota / oauth / tester）无需改动——常量已在上一轮收口。
3. 拉取失败保留上次值，绝不回退到空值。设置页允许手工覆盖并锁定（`codex_client_version_locked`）。

**验收标准**：同步任务写入版本后，抓包确认出站 UA 已变；断网时沿用旧值不报错；手工锁定后自动同步不覆盖。

---

### 3.2 分组级利润控制

**现状**：`account_groups.rate_multiplier`（[schema.ts:33](../src/db/schema.ts#L33)）已有计费倍率，但**没有按利润率过滤调度候选**的能力。对应 sub2api v0.1.170。

**实现要点**
1. `account_groups` 加 `min_profit_rate DOUBLE PRECISION`（null = 关闭）、`profit_buffer DOUBLE PRECISION NOT NULL DEFAULT 0`。
2. 调度时（`src/accounts/scheduler.ts`）估算候选账号的**上游成本**与**向用户收取的价格**（`base_cost × rate_multiplier`），利润率低于阈值的候选剔除；全部被剔除时降级为「按利润率排序取最优」而非直接 503（避免全线不可用）。
3. 槽位占用后二次复核，防止并发下超卖。
4. **默认关闭**，且需要账号级上游成本倍率作为输入——首期用分组配置的固定倍率近似，不做自动探测。

**风险**：直接影响可用性。必须默认关闭 + 有降级路径 + 管理端明确提示。

---

### 3.3 用户分平台配额

**现状**：`users` 表只有 `concurrency_limit` 与 `balance_micros`（[schema.ts:123](../src/db/schema.ts#L123)），无按平台 + 时间窗的 USD 上限。已有的 `subscription_plans` 提供了**按分组**的日/周/月窗口（[schema.ts:62](../src/db/schema.ts#L62)），但维度是分组不是 provider。对比文档第 14 项。

**实现要点**
1. 新表 `user_provider_quotas`：`user_id` / `provider` / `daily_limit_usd` / `weekly_limit_usd` / `monthly_limit_usd` / 三个 `window_start` / 三个 `usage_usd`，主键 `(user_id, provider)`。
2. **复用 `src/subscriptions/manager.ts` 已有的滚动窗口推进与扣减逻辑**，不要重写一套——把窗口推进抽成共用函数，两处调用。
3. 校验时机：`src/middleware/apiKeyAuth.ts` 请求准入时检查，`src/usage/recorder.ts` 计费时累加。超限返回 429 并带明确的窗口重置时间。
4. 管理端在用户详情页配置；用户端在概览页展示各平台已用 / 上限进度条。
5. 优先级：`per-key quotaLimit` → `user_provider_quota` → `subscription` 窗口，任一命中即拒绝，日志里标明是哪一层拦的。

**验收标准**：单测覆盖窗口跨天推进、多平台隔离、三层限制的优先级与错误信息区分。

---

### 3.4 聚合（composite）分组 ★本阶段最大改动，放最后

**价值**：本仓库已支持 claude / openai / gemini / grok / deepseek / xiaomi / zhipu / qwen / kimi / sub2api **十个上游**（[registry.ts](../src/providers/registry.ts)），但一个 API Key 只能绑一个分组。聚合分组让**一把 Key 按模型路由到不同平台的子分组**，是多上游能力的关键放大器。对应 sub2api v0.1.164。

**实现要点**
1. `account_groups` 加 `kind TEXT NOT NULL DEFAULT 'plain'`（`plain` | `composite`）。
2. 新表 `composite_group_rules`：`id` / `group_id` / `match_type`(exact|prefix|regex) / `pattern` / `target_group_id` / `target_model`（可选，转发时改写模型名）/ `priority` / `enabled`。
3. 路由解析在 `src/keys/modelMapping.ts` 之后、调度取号之前：请求模型逐条匹配规则（按 priority），命中即把调度范围限定到 `target_group_id`，未命中走分组默认子组或返回 404（**沿用现有语义：未知模型 404，无可用账号 503**）。
4. **结算按实际转发的分组与模型**：`rate_multiplier` 取子分组的，`usage_logs.model` 记改写后的模型，同时用 2.1 新增的 `upstream_model` 记上游声明值。
5. 防环：`target_group_id` 不允许指向 composite 分组（单层），保存时校验。
6. 管理端提供规则编辑器 + **「模拟路由」预演**：输入模型名，展示会命中哪条规则、落到哪个分组、按什么倍率计费。

**验收标准**：单测覆盖三种匹配类型、优先级、未命中、防环校验、结算取子组倍率；端到端验证一把 Key 同时打通 Claude 与 GLM。

**风险**：改动调度取号路径。必须在 `plain` 分组上做全量回归，确认非 composite 场景**零行为变化**。

## 阶段四 · 协议覆盖（P3）

> 目标：补齐 OpenAI 兼容协议的缺失端点，让 Dify / RAGFlow / FastGPT 这类客户端能直接接入。三项都是「新增端点、不动既有路径」，风险最低，可与阶段三并行。

### 4.1 `/v1/embeddings` 网关

**现状**：全仓无 embeddings 实现。这是 RAG 类客户端接入的**硬门槛**——没有它，Dify 之类工具连不进来。

**实现要点**
1. 新增 `POST /v1/embeddings` 与 `/api/{provider}/v1/embeddings`，走现有 `requireApiKey` 与调度链路。
2. 首批支持：OpenAI（`text-embedding-3-*`）、智谱（`embedding-3`）、通义（`text-embedding-v3`）、DeepSeek（若上游支持）。各 provider 补 `embeddings.ts`。
3. 计费：`model_pricing` 已有 `input_price`，embeddings 只有输入 token，输出计 0。usage 记录 `provider` + `model`，`status` 复用现有语义。
4. 支持 `input` 为 string / string[] / token 数组三种形态，以及 `encoding_format: float|base64`。

---

### 4.2 `/v1/audio/*`（TTS / STT）

**实现要点**
1. `POST /v1/audio/speech`（TTS，返回音频流）、`POST /v1/audio/transcriptions` 与 `/translations`（STT，multipart 上传）。
2. 复用 images 端点已有的 `bodyLimit: imageBodyLimit` 模式处理大文件体（[relay.ts:1125](../src/routes/relay.ts#L1125)），单独给音频设更大的 `audioBodyLimit`。
3. 计费：TTS 按字符数、STT 按音频秒数。`model_pricing` 需扩展两列 `char_price` / `second_price`，或复用 `input_price` 并在 usage 里用 `image_count` 同款的计量列——**倾向新增独立列，语义更清晰**。
4. 开关 `AUDIO_GATEWAY_ENABLED`，默认关闭（多数自托管用户用不到，避免扩大攻击面）。

---

### 4.3 `/v1/rerank` 网关

**实现要点**：`POST /v1/rerank`，转发到智谱 / 通义 / Cohere 兼容上游。按 query + documents 的总 token 计费。实现最简单，与 4.1 同批提交。

## 阶段五 · 运营与生态（P4）

> 目标：面向「对外开放的拼车站」场景。**如果只自用或小圈子用，本阶段可整体推迟。** 各项之间无依赖，可按实际需求单独挑。

### 5.1 SMTP 邮件通知

**现状**：全仓**零通知能力**（无 `smtp` / `nodemailer` 任何痕迹）。账号 OAuth 失效、余额耗尽、配额熔断全靠人工盯后台。这是本阶段里**最实用的一项，建议优先做**。

**实现要点**
1. 新增 `src/notify/mailer.ts`，SMTP 配置存 `settings`（密码加密），提供 `sendMail(to, subject, body)` 与「测试发送」接口。
2. 通知事件（每项可独立开关）：
   - 账号 OAuth 永久失效（复用 `src/accounts/refreshErrors.ts` 已有的永久失败分类）
   - 账号配额自动暂停 / 全部账号不可用
   - 用户余额低于阈值 / 订阅到期前 3 天
   - 计费熔断触发（阶段一 1.5）
   - 支付回调异常
3. 发送走队列 + 退避重试，失败不阻断主流程。同类事件做**去重与聚合**（如 10 分钟内同一账号只发一次），避免刷屏。
4. 收件人：管理员邮箱（settings）与用户自身邮箱（`users.email`）分别路由。

### 5.2 公告系统

新表 `announcements`（`id` / `title` / `content` / `level` / `starts_at` / `ends_at` / `published` / `created_at`）。管理端增删改 + 预览；用户端登录后在概览页顶部展示，支持「不再提示」（localStorage 记 ID）。落地页也可展示。

### 5.3 邀请返利

在已有的 `user_invites`（[schema.ts:137](../src/db/schema.ts#L137)）基础上扩展：新表 `referral_rewards`（`inviter_id` / `invitee_id` / `amount_micros` / `status`(frozen|settled|revoked) / `frozen_until` / `created_at`）。规则：按被邀请人首充或消费额的百分比返利、冻结期（防刷单后退款）、单人上限、专属邀请码。结算走已有的 `wallet_transactions` 账本，类型加 `referral`。管理端可配比例与冻结天数，并查看返利明细。

### 5.4 Stripe / EasyPay 国际支付

已有的支付抽象在 `src/payments/providers/base.ts`，`alipay.ts` / `wechat.ts` 是现成模板。新增 `stripe.ts`（Checkout Session + Webhook 验签）与 `easypay.ts`。注意复用现有的**幂等入账**逻辑（`src/payments/manager.ts`），退款路径需按 sub2api v0.1.171 的教训做**重复退款保护**与余额不足时的显式强制确认。

### 5.5 钉钉 OAuth 登录

在 `src/routes/auth.ts` 增加第三方登录入口，`users` 加 `external_provider` / `external_id`（唯一索引）。首次登录按邮箱匹配已有账号或新建（受 `registration_enabled` 控制）。同一套抽象后续可扩展飞书 / 企业微信。

### 5.6 Antigravity 上游

按 `src/providers/gemini/` 的模式新增 `src/providers/antigravity/`，注册进 `registry.ts`，补 relay / usage / 定价。支持 Gemini 3.6 Flash 系列（sub2api v0.1.172 已适配）。

### 5.7 Ollama Cloud 上游

新增 `src/providers/ollama/`，API Key 接入，用量按请求驱动刷新（对齐 sub2api v0.1.165 做法，避免定时轮询）。

## 附录 C · 明确不做 / 暂缓的项

以下 sub2api 能力经评估**不纳入本计划**，理由是与「轻量自托管」定位错位，或依赖本仓库没有的架构：
