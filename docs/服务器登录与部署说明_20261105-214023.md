## 当前项目的独立登录入口

- 入口：`scripts/server-ssh.mjs`，仅使用本项目的 `ssh2` 开发依赖。
- 本机凭据：`.deployment/ssh.local.json`。已在这台电脑配置，无需再读取其他项目。
- 凭据目录已同时加入 `.gitignore` 和 `.dockerignore`，不提交到 Git、不进入 Docker 构建上下文。
- 口令使用 Windows 当前用户加密保存，脚本只在内存中解密，不把口令放入命令行参数。
- 主机密钥使用当前用户 `~/.ssh/known_hosts` 中的已有记录校验，支持普通和散列主机名；不跳过主机校验。

在仓库根目录执行连接检查：

```powershell
node scripts/server-ssh.mjs check
```

该检查读取主机身份、主容器状态、运行版本和健康状态，不执行部署。如果提示缺少 `ssh2`，先在仓库根目录按锁文件安装开发依赖：`npm ci`。

执行本机保存的远程 Bash 脚本：

```powershell
# 普通 ubuntu 用户
node scripts/server-ssh.mjs run .deployment/check.local.sh

# 通过 sudo -n 以 root 执行
node scripts/server-ssh.mjs sudo-run .deployment/deploy.local.sh
```

脚本会把 CRLF 换行为 LF，并传回远程退出码。不要让远程脚本输出服务器 `.env`、完整 Compose 配置或其他业务凭据。

## 本机凭据的保存与迁移

当前 `.deployment/ssh.local.json` 的非敏感字段为：

```json
{
  "host": "43.130.139.222",
  "port": 22,
  "username": "ubuntu",
  "credentialProtection": "windows-dpapi-current-user",
  "passwordProtected": "由当前 Windows 用户加密的口令，实际密文仅保存在本机配置文件"
}
```

DPAPI 密文绑定保存时的 Windows 用户和电脑。更换电脑或用户时，需要重新配置口令并核验服务器主机密钥，不能仅复制密文后使用。

需要重新保存口令时，在本机 PowerShell 中交互输入；以下操作不会把明文口令写入历史记录：

```powershell
Import-Module "$PSHOME/Modules/Microsoft.PowerShell.Security/Microsoft.PowerShell.Security.psd1" -ErrorAction Stop
$securePassword = Read-Host 'SSH 登录口令' -AsSecureString
$config = [ordered]@{
  host = '43.130.139.222'
  port = 22
  username = 'ubuntu'
  credentialProtection = 'windows-dpapi-current-user'
  passwordProtected = ConvertFrom-SecureString $securePassword
}
New-Item -ItemType Directory -Path .deployment -Force | Out-Null
$config | ConvertTo-Json | Set-Content -LiteralPath .deployment/ssh.local.json -Encoding utf8
```

自动化环境也可通过进程环境变量 `MODEL_BRIDGE_SSH_PASSWORD` 提供口令；该变量优先于本机密文。不要把变量值写入可提交的脚本或文档。

## 部署前提与流程

1. 在本机完成必要验证，并将要部署的版本提交、推送到远程 `main`；明确记录目标完整提交 SHA。
2. 运行上述 `check`，确认连接到 `43.130.139.222`，主服务正常，`sudo -n` 可用。
3. 核对服务器工作区没有受跟踪文件改动；发现改动时停止，不能用 `reset --hard` 覆盖。
4. 保留服务器 `.env`、`data/` 和下文的 `docker-compose.override.yml`。
5. 在服务器项目目录构建主服务及更新器，再仅重建这两个服务；普通应用更新不重启数据库及其他项目。

把下列 Bash 内容保存到本机 `.deployment/deploy.local.sh`，将 `expected_sha` 替换为已推送的目标完整 SHA，再通过 `sudo-run` 执行：

```bash
set -euo pipefail
cd /home/model-bridge
expected_sha=替换为已提交并推送的完整SHA

if [ -n "$(git status --porcelain --untracked-files=no)" ]; then
  printf '服务器存在受跟踪文件改动，停止部署\n' >&2
  exit 1
fi
test -f docker-compose.override.yml
git fetch origin main
# 先确认本次部署的目标，避免意外合入其他更新。
test "$(git rev-parse origin/main)" = "$expected_sha"
git merge --ff-only origin/main
test "$(git rev-parse HEAD)" = "$expected_sha"
export BUILD_COMMIT="$expected_sha"
docker compose config --quiet

# 构建失败时，原有运行容器继续服务。
docker compose build model-bridge model-bridge-updater
docker compose up -d --force-recreate --no-deps model-bridge-updater model-bridge

# 等待新服务启动。
curl --fail --silent --show-error --retry 20 --retry-connrefused \
  --retry-delay 2 --retry-max-time 90 http://127.0.0.1:3001/health
printf '\n'
docker exec model-bridge node --input-type=module -e \
  'import { readFileSync } from "node:fs"; console.log(JSON.stringify({version: JSON.parse(readFileSync("package.json", "utf8")).version, commit: process.env.GIT_COMMIT}))'
```

重建前记录两个容器的镜像 ID，保留旧镜像供验证失败时回退。不要执行 `docker compose down -v`、清空 `data/` 或全局 Docker 清理。

## 更新器的宿主机路径覆盖配置

服务器 `/home/model-bridge/docker-compose.override.yml` 已配置如下内容。这是服务器本机配置，当前未纳入 Git：

```yaml
services:
  model-bridge-updater:
    environment:
      REPO_DIR: /home/model-bridge
    volumes:
      - /home/model-bridge:/home/model-bridge
```

保留这份覆盖配置。它使更新器容器内的 Compose 工作目录和宿主机绝对路径一致，否则容器内 `/repo` 可能被误当作宿主机目录，导致主服务绑定到错误的 `/repo/data`。

正确的数据挂载为：

- 主服务：`/home/model-bridge/data` → `/app/data`。
- PostgreSQL：`/home/model-bridge/data/pg` → `/var/lib/postgresql/data`。

如果这份覆盖配置缺失，先按上面的内容恢复，并执行 `docker compose config --quiet`；不要覆盖已存在且内容不同的服务器配置。

## 部署后的确认

- 运行 `node scripts/server-ssh.mjs check`，核对输出的版本和提交 SHA。
- 确认公网 `/health` 返回 `{"status":"ok","service":"model-bridge"}`。
- 在后台“系统更新”检查更新器可用、工作区干净、运行版本与远端一致。
- 确认主服务数据挂载仍是 `/home/model-bridge/data`，PostgreSQL 和其他项目没有被重建。
