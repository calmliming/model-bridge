### 第一批修复范围

#### F01 GPT-6.1 Terra

[pricing.ts](../src/usage/pricing.ts) 的 openaiPrice 从第 294 行开始，仅专门识别 GPT-6.1 Sol；第 184 行的通用 GPT 兜底价为输入 1.25、输出 10、缓存读取 0.125、缓存写入 0 美元每百万 Token。本地直接调用 resolvePrice 得到的 Terra 结果正是该兜底价格。

[上游 Terra 提交](https://github.com/Wei-Shaw/sub2api/commit/34236674223877d265bb5dbc071277d04ded0d34)中的标准兜底价为输入 1、输出 5、缓存读取 0.05、缓存写入 1.25。这里是两个仓库的默认配置对比；落地价格仍应结合实际供应商、账号类型和运营配置核定。已配置精确模型价格覆盖的部署不一定受默认值影响。

#### F02 Responses 缓存命中

缺口位于 [DeepSeek Responses 用量解析](../src/providers/deepseek/responses-usage.ts)第 16 行、[OpenAI Responses 用量解析](../src/providers/openai/usage.ts)第 34 行，以及 [Responses 转 Chat 用量](../src/providers/openai/chat.ts)第 321、332 行。Chat 原生用量解析第 345 行已经支持 prompt_cache_hit_tokens。

补齐标准嵌套字段、顶层 cached_tokens、prompt_cache_hit_tokens 的回退顺序，并同步修正返回给客户端的 Chat usage。标准字段明确为 0 时应保留 0，不用真假值判断覆盖；缓存 Token 不能既计入普通输入又重复计缓存费。验收同时覆盖流式、非流式、字段缺失和多字段并存。

#### F03 非流式 SSE 响应识别

[relay.ts](../src/routes/relay.ts)第 1518、1533、3350 行分别在读取、失败检查、响应转换时依赖 text/event-stream。应在有限前缀内识别可信的 SSE 帧格式，并让这些分支使用同一判定结果。上游依据为[缺少响应头的 OAuth 非流式修复](https://github.com/Wei-Shaw/sub2api/commit/4db8402b5)。

验收包含无 Content-Type、text/plain、application/octet-stream、正常 JSON，以及包含 data: 文本的普通内容。应验证返回 JSON 格式、计费、语义失败重试和终止条件。旧清单建议的简单多行正则存在把普通正文误判成 SSE 的可能，不宜直接作为最终实现。

#### F04 国产上游限流分类及 Kimi 并发 403

[relay.ts](../src/routes/relay.ts)第 1206 行的 429 分类会读取通用重置提示，但缺少国产供应商的频率与套餐耗尽分支；第 1332 行应用惩罚。[scheduler.ts](../src/accounts/scheduler.ts)第 9 行的默认 rate_limited 冷却为 10 分钟。

对智谱、Kimi、Qwen、MiniMax 等实际支持的账号类型，按供应商错误码、额度证据和 Retry-After 区分短期频率限制、套餐窗口耗尽、余额不足。已有有效重置时间应继续优先使用；缺乏证据的 quota 文案不应一律视作瞬时限频，也不应凭空设置为五小时停调。

验收覆盖同号退避、跨号切换、短冷却恢复、额度耗尽、模型级限制和重试取消，保持总尝试次数有界。当前问题是部分瞬时 429 缺少提示时默认停调过久，并非所有国产 429 都忽略重置时间。[上游 v0.2.19 说明](https://github.com/Wei-Shaw/sub2api/releases/tag/v0.2.19)

11 月 5 日增补：[Kimi 新修复](https://github.com/Wei-Shaw/sub2api/pull/8503)与本项目存在直接对应。relay.ts 第 872 行精确识别并发上限文案，第 1282–1289 行把它归为账号级 rate_limited；没有重置提示时 resetAt=null，scheduler.ts 第 196 行使用十分钟默认值。本地调用分类函数已复现该结果；带 Retry-After: 5 时已有重置时间，应保留。建议针对精确并发 403 设置可配置的秒级兜底冷却，并保持余额耗尽、鉴权错误及相近但不同的权限文案各自行为。验收连续触发不会逐次延长成分钟级停调，以及存在更长有效额度冷却时不会被短冷却错误清除。

#### F05 Gemini 生图计量

### 第二批可靠性与管理改进

#### F06 有界读取最终用量

[relay.ts](../src/routes/relay.ts)第 2215 行在下游关闭时立即取消上游，第 3124–3149 行会记录已收到的用量并标记 client_disconnected。现有集成测试也覆盖断开后的入账和资源释放，所以应描述为尾包可能缺失，而不是断开后完全不计费。

对已开始响应、仅等待尾包的情况，可评估独立的短时排空预算；提前取消和错误中止仍应及时结束工作。需要区分下游停止写入与上游停止读取，避免重复结算，并覆盖超时、挂起上游、并发槽、余额预留释放和资源回收。默认预算应经过行为测试确定，不能直接照抄固定三秒作为既定需求。

#### F12 受限管理员 Key

[adminAuth.ts](../src/middleware/adminAuth.ts)目前只验证 JWT；[admin.ts](../src/routes/admin.ts)第 539–554 行登录签发七天会话，入口可启用 Turnstile。用于模型调用的 [apiKeyAuth.ts](../src/middleware/apiKeyAuth.ts)不是管理接口授权系统。

若需要自动化运维，应新建独立凭证与策略，初版覆盖 accounts.read、quota.read 等只读操作，按账号或分组范围检查；创建、修改调度、重置额度、余额调整分别授权。已有 OpenAI 查询/重置能力位于 admin.ts 第 1593、1610 行，不需要因上游新增权限而重做业务功能。

当前管理 JWT 没有会话版本撤销检查，角色缺失时也会通过 requireAdmin 的角色分支；现有签发点明确带角色，这不等于已确认外部越权漏洞，但扩展凭证类型前应改为显式校验管理员角色并设计撤销机制。现有调用日志和钱包流水也不等同于管理操作审计。旧清单把本项估为中等工作量、低风险偏乐观，本次列为 L。[上游权限设计](https://github.com/Wei-Shaw/sub2api/pull/8476)

### 后续功能与无需重复开发的项目

#### F13 管理 MCP

上游的 [MCP 设计](https://github.com/Wei-Shaw/sub2api/blob/4a4a83ee5/docs/mcp.md)包括 OAuth/PKCE、个人和管理员范围、只读和读写权限、授权撤销、短期访问令牌、刷新轮换、工具白名单及操作审计；默认关闭，管理员读写授权还要求二次验证。

### 本轮新增跟进项

#### F15 SSE 和非流式响应大小边界

对应 [PR 8484](https://github.com/Wei-Shaw/sub2api/pull/8484)。[relay.ts](../src/routes/relay.ts)第 2988–2994 行持续读取上游并累积未完成的事件文本；[streamPeek.ts](../src/providers/streamPeek.ts)第 49–96 行保留预读字节和文本，但只有时间预算，没有字节预算；[openai/sse.ts](../src/providers/openai/sse.ts)第 15 行会收集整个非流式 Responses 转换所需的 transcript。返回响应头后的读取也没有统一的应用层空闲期限。

应给单个 SSE 行/事件、首包预读与重放、非流式全文分别设置上限，并在读取过程中计量，不能等 text() 或 JSON.parse 完成后才检查。普通原生流式输出应按帧约束，不能把正常长对话误当成超大非流式缓冲。图片帧需要独立、明确的尺寸预算；上游保留 500 MiB 默认单行兼容限额是它的部署选择，不作为本项目默认值。

验收包括缺少空行结束符的持续事件、多行小 data 累积、注释/心跳、合法大图片、超过边界、首包前后报错及连接取消。已发响应头时返回协议内错误，取消上游并释放槽位，不能生成成功 completed。另给上游读取设计可配置空闲期限；本项目的 connect/header 十秒超时在收到响应后已经清除，不是整个流的读取保护。

已有 [streamWriter.ts](../src/http/streamWriter.ts)第 4–25 行处理背压、关闭信号与默认三十秒 drain 超时，本轮相关测试通过。这部分不重复开发；也不把 Go 字符串拼接的分配结论直接套到 JavaScript，优化复制开销需单独测量。

#### F16 入站内存预算与上传期限

对应 [PR 8484](https://github.com/Wei-Shaw/sub2api/pull/8484)。[index.ts](../src/index.ts)第 67 行附近设置全局 32 MiB bodyLimit；[relay.ts](../src/routes/relay.ts)第 1570–1573 行把图片和多模态入口提高至 64 MiB。模型 API 鉴权在 preHandler，用户/Key 并发与余额预留在 executeRelay 内执行，均晚于请求体读取解析。[admission.ts](../src/usage/admission.ts)限制的是请求数量与资金预留，不是上传阶段的内存字节。

本地用仓库安装的 Fastify 和相同基础配置检查，requestTimeout 与 connectionTimeout 均为 0。反向代理可能另有限制，但应用当前没有显式上传读取期限。许多尚未进入 executeRelay 的上传可以同时各自满足单请求大小限制，不能由后置并发控制保护这部分内存。

建议在读取/解析前增加实例级预算，并区分临时容量不足与单请求超限；对未知长度上传增量计量，覆盖原始 Buffer、JSON/表单转换、base64 和仍被长请求持有的副本。明确预算是应用管理的存储估算，不等同于进程 RSS。设置上传读取期限并在正常完成、拒绝、取消、解析失败时释放预算，保持健康的长时间输出。不要为了照搬上游而新增本项目没有的解压缩路径。

验收需覆盖多个合规大上传同时进入、未知长度、认证失败、解析失败、取消和压力恢复；数值由实例内存与实测并发决定。本轮没有执行大流量或耗尽内存的压测，优先级依据当前可见的生命周期缺口。

#### F17 Grok 代理消息输入

对应 [PR 8465](https://github.com/Wei-Shaw/sub2api/pull/8465)。[grok/relay.ts](../src/providers/grok/relay.ts)第 197–207 行对非工具输出条目直接保留，第 294–306 行的主归一入口没有 agent_message 分支。[agentMessage.ts](../src/providers/agentMessage.ts)已能按顺序提取文本和自定义协议中以 encrypted_content 字段承载的明文，Kimi/Qwen/智谱/小米转换已经复用它。

本地样例把两个片段传入 Grok 归一入口，输出仍然是 agent_message；共享函数能得到完整的 Task: check gateway。建议在 Grok 原生 Responses 输入处转换为普通 user message，保留原始片段顺序和空白；空正文可跳过。不得只删除条目、仅保留信封，或尝试解密原生 reasoning 密文。

验收覆盖混合对话历史、工具结果邻接、字符串/数组内容、空片段和流式/非流式外部入口。当前不是缺少全项目共用能力，而是 Grok 分支漏接，适合独立小改动。

#### F18 OpenAI instructions 回显

对应 [PR 8499](https://github.com/Wei-Shaw/sub2api/pull/8499)。[openai/relay.ts](../src/providers/openai/relay.ts)第 175 行会给缺失、null 或空字符串的 instructions 补默认文本；纯空白字符串保留。本项目没有上游那种要求非空否则返回 403 的分支，不能照搬“删除拒绝逻辑”。

[responseFields.ts](../src/providers/openai/responseFields.ts)只补响应时间和事件序号，没有按客户端请求恢复 instructions。样例确认默认文本会被响应归一器保留；若上游回显修改后的内容，客户端看到的便不是原请求值。默认模板目前很短，不能套用上游两万多字符的放大程度，也没有证据把它认定为密钥泄漏。

在适配入口保存客户端原值并标记是否发生网关补写，仅在确实改写的路径还原对应响应字段；覆盖原生 SSE、JSON 及 SSE 转 JSON，避免污染重试状态或其他供应商响应。是否保留默认补写与是否还原回显分别定义，不因这项修复删掉客户端明确提供的指令。原值为缺失、null、空白和多行 JSON 的情况均需验证 SSE 帧仍合法。

#### F19 生图尺寸路由

对应 [PR 8462](https://github.com/Wei-Shaw/sub2api/pull/8462)。[images.ts](../src/providers/openai/images.ts)已有尺寸校验和 imageSize 记录；[scheduler.ts](../src/accounts/scheduler.ts)第 42 行的选号参数只有 provider、排除账号、会话、分组和模型，没有请求尺寸，也没有读取账号的尺寸能力声明。

如果同组存在只支持较小图片的账号与支持 4K 的账号，增加明确的能力列表，并在选号、重试、粘性账号复查和账号测试时共同使用。识别不到尺寸时不能无条件排空账号池；保持原有粘性语义。区分整组不支持目标尺寸的 400 与账号暂时冷却/忙碌的 503。业务若还需要尺寸维度冷却，应单独设计；上游该 PR 首先增加能力过滤，不能宣称它已把所有冷却都改为账号加模型加尺寸。

这是能力选择，不代表本项目必须同步采用上游的按尺寸价格。现有 GrsAI 模型及持久化媒体任务也不能因为都生成图片就无差别套用 OpenAI 账号规则。无混合尺寸账号池时维持 P2 条件项。

#### F20 Antigravity 系统身份前缀

仅在 Antigravity 适配边界匹配已知系统块开头的身份声明和 attribution 元数据，并保留后续任务正文、模型引用、用户消息及工具描述。处理逻辑需覆盖当前实际支持的 Messages 和原生 Gemini 入口，不为跟进补丁额外增加新的协议路由。验收字符串/数组系统提示、多个系统块、已经有 Antigravity 身份块及包含真实任务的身份前导。该项是兼容增强，不能承诺能消除上游 429。

#### F21 粘性缓存硬上限

对应 [PR 8484](https://github.com/Wei-Shaw/sub2api/pull/8484)。[accounts/session.ts](../src/accounts/session.ts)第 20 行的 SWEEP_THRESHOLD=10000 仅触发过期扫描；第 75–76 行扫描后仍继续 set，因此一万个未过期会话不是硬上限，超过阈值后的每次新增还会扫描整个 Map。没有后续访问时，过期项也不会自动回收。

对未配置 Redis 的进程内实现增加条目上限、明确的淘汰顺序及一个受生命周期管理的清理任务；避免每键定时器或每次写入全量扫描。配置 Redis 时已有键 TTL，应区分内外两条路径。验收容量压力、到期清理、热点会话、失效绑定回退和关闭清理。

不把所有缓存都判为无界：[Antigravity 签名缓存](../src/providers/antigravity/signatures.ts)已有 16 MiB、5000 项和单签名大小约束；Codex manifest 也已有条目上限，其并发问题仍由 F08 处理。

#### F22 计费后台工作的边界

对应 [PR 8484](https://github.com/Wei-Shaw/sub2api/pull/8484)。[recorder.ts](../src/usage/recorder.ts)第 219 行已经在写库前复制用量并持久化 outbox，第 235 行用单个 replaying Promise 合并重放，[durableQueue.ts](../src/usage/durableQueue.ts)每次读取最多 100 条，重放按顺序执行。因此不需要重做一套“从无到有”的可靠队列，也没有 Go Gin context 池复用的同构问题。

仍需改进的是实时 recordUsage/recordStreamUsage 调用的全局写入背压，以及数据库操作等待期限。pendingUsageWrites 是跟踪集合，不是执行器上限；[db/index.ts](../src/db/index.ts)只配置连接等待超时，没有在该处设置语句超时。限流和并发配置可能降低压力，但不替代后台写入边界。

先量化持续数据库故障下的积压与恢复，设置可观察的队列/并发和 I/O 期限，保持已持久化账目可重放、幂等与原价格快照。容量耗尽不能静默丢账；同步回退也不能绕过整体上限。验收正常关闭、数据库长时间等待、失败恢复、重复提交和满载策略。当前代码已有停机等待及重试任务清理，应沿用。

#### F24 Windows 目录同步兼容

本项是此次本地回归发现，与 Sub2API 的提交没有直接一一对应。七个相关测试文件共 142 个用例，138 通过、4 失败；失败都发生在 [durableQueue.ts](../src/usage/durableQueue.ts)第 22–24 行对目录调用 FileHandle.sync()，返回 EPERM。独立空目录样例在本机 Windows/Node 24.22.1 同样复现，排除了只由测试断言造成的解释。

受影响的是 outbox 的写入、确认及延迟重试的目录同步步骤，可能使恢复流程抛错。不能据此断言全部账单丢失：重命名、删除或数据库结算可能已发生；更不能将 Windows 的结果推定为 Linux 容器故障。

修复应明确不同平台的持久化能力，保留文件同步、原子替换和幂等结算，并区分目录同步不支持与真实权限/磁盘错误；不要全局吞掉所有 EPERM 或 fsync 错误。验收本地失败用例、重启恢复、提交结果不确定时的重放，并在目标部署平台验证。原生 Windows 生产部署升 P1，当前本地开发兼容项列 P2。
