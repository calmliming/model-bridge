# tokens/s 残留上一轮数值：根因与修复

## 1. 现象

在 Claude Code 中经 model-bridge 使用 DeepSeek 时，新一轮思考开始，界面先显示上一轮的速率
（例如 300 tokens/s），停留一段时间后才归 0，然后才正常累加。

## 2. 根因（已在 Claude Code v2.1.268 二进制中逐行确认）

Claude Code 的 tokens/s 由一组内部 `api_metrics` 事件驱动：

```
start              { ttft_ms, message_id }
end                { output_tokens }
content_block_start
thinking_progress  { estimated_tokens_delta }
thinking_signature { chars }
```

计数器条目由 `Sqn` 维护，**只有 `start` 会新建条目**：

```js
if (c.type === "start")
  return t.push({ id: c.id, ttftMs: c.ttftMs, firstTokenTime: Date.now(),
                  lastTokenTime: Date.now(), responseLengthBaseline: s, endResponseLength: s }), s
let l = c.id != null ? t.find(m => m.id === c.id) : t.findLast(m => m.id == null)
if (!l) return s
if (c.type === "content_block_start") return l.thinkingTokenEstimate = 0, ...
```

而 `start` 只在收到 SSE `message_start` 时发出：

```js
if (e.event.type === "message_start") {
  if (e.ttftMs != null) d?.({ type: "start", ttftMs: e.ttftMs, messageId: e.event.message.id })
  ...
}
```

`content_block_start` 只重置块内基线，不新建条目。

**结论**：条目数组 `_apiMetrics` 跨轮次累积，渲染取 `findLast`。在新一轮的
`message_start` 抵达之前，界面渲染的仍是**上一轮那条已完成的条目** —— 于是旧速率原样留在屏幕上。
残留时长 = 「转轮出现」到「`message_start` 送达」之间的全部时间。

这是客户端显示逻辑，任何上游/网关都会触发；网关能做的只有一件事：**让 `message_start` 尽早送达**。

## 3. 网关侧实测（172.16.3.127:8080，LAN）

| 测量项 | 结果 |
| --- | --- |
| `/health`（无鉴权、无 DB） | 9–14 ms |
| `/v1/models`（鉴权 + DB 读） | 9–15 ms |
| `/v1/messages` 到 `message_start` | 734 / 807 ms |

网关自身固定开销约 10 ms，其余为上游 TTFT（上游把响应头一直压到首个 token 才发出，
`headers` 与 `message_start` 同一毫秒到达）。

## 4. 发现的真实缺陷

`runRelayLoop` 在**拿到上游响应头之后、调用 `sendStreaming` 之前**串行 `await` 了三类纯记账写入：

- `updateAccountQuota()` —— Postgres 写
- `markAccountUsed()` —— Postgres 写
- `bindStickyAccount()` —— Redis 写

此时上游的 `message_start` 已经躺在 socket 缓冲里，但网关还没往下游写第一个字节。
这几次往返被精确地插在「上游首帧可读」与「下游首帧写出」之间，
等价于让上一轮的速率多冻结同样长的时间。三者都只影响**后续请求的调度**，与本次响应无关。

## 5. 修复

`src/routes/relay.ts`：把这三类写入改为并发发起，由该次 attempt 的 `finally` 统一回收。

- 成功路径：`finally` 在流结束后才执行，等待成本为零。
- 重试路径：`continue` 前照常回收，行为不变。
- 用 `.catch()` 包裹并记 warn，避免 unhandled rejection；请求不会早于自身写入结束。

配额触发自动暂停的分支（`penalizeAccount`）一并移入同一延后任务，逻辑不变。

## 6. 回归测试

`src/routes/relay.integration.test.ts` → `stream first-frame latency`：
把 `markAccountUsed` 挂在一个手动释放的 Promise 上，断言**首帧 `message_start` 先于记账写入抵达**。

- 修复前：请求被记账写入卡住，测试 5 s 超时失败。
- 修复后：通过。

全量：`tsc --noEmit` 通过，718 passed / 11 skipped。

## 7. 仍未消除的部分

主要残留时长来自上游 TTFT（本次实测 ~730–800 ms），与网关无关，直连同样存在。
要彻底消除只有一条路：网关在上游响应前抢先下发一个合成的 `message_start`。
代价是必须提前提交 HTTP 200，**多账号故障转移会随之失效**——不划算，未采用。
