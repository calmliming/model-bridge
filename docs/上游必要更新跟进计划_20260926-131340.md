# 上游必要更新跟进计划

核查日期：2026-09-26（北京时间）。本地代码基线：`264f50b`。

本计划参考 Sub2API v0.2.8、New API v1.0.0-rc.40 及本次已核实的后续主线修复，只安排与 model-bridge 现有转发路径有关的工作。状态为**已实施并完成本地验证**（2026-09-26）。第二节保留实施前的纯函数复现证据；实施结果见第八节。未做真实供应商接口联调或生产部署。

## 一、结论与实施顺序

建议先处理四项已确认的协议缺口，再补用量可观测性和模型目录。估算扣费与平台级新能力单独评估。

| 顺序 | 优先级 | 跟进项 | 本地结论 | 完成目标 |
| --- | --- | --- | --- | --- |
| 1 | P1 | Responses → Chat 主动请求流式 usage | 四个转换器会丢掉 `stream_options`，与现有原生 Chat 路径行为不同 | 能收到供应商提供的最终真实用量 |
| 2 | P1 | Chat → Responses 分段与终态 | 已关闭 reasoning 项仍接收 delta；空流会合成成功 | 客户端事件顺序正确，异常结束不伪装成完成 |
| 3 | P1 | 工具结果图片转换 | 部分路径将图片编码进工具文本，另一些直接丢图 | 图片作为图片发送，保留并行工具回复顺序 |
| 4 | P1 | 智谱 Responses 推理强度映射 | 原生 Chat 已透传；Responses 转换会遗漏 | 支持范围内的推理强度实际送达上游 |
| 5 | P2 | 缺失用量可观测性 | 未收到 usage 与真实零用量无法区分 | 日志可区分真实、部分、缺失与历史未知用量 |
| 6 | P2 | Grok 4.7 目录与定价核实 | 目录停在 4.6，4.7 会落到 4.5 价格兜底 | 型号与价卡来源明确，保留已有自定义价格优先级 |

P1 是本轮推荐实施范围。P2 可随后处理；其中 Grok 4.7 的实际价格必须先核实，不能根据上游新增模型名称推断价格。

## 二、本轮核查证据

没有使用模型凭据、数据库或真实供应商请求。通过 `node --import tsx --input-type=module` 在内存中调用当前转换器和 usage parser，得到以下结果：

| 输入样例 | 当前结果 | 受影响范围 |
| --- | --- | --- |
| Responses 请求显式带 `stream_options.include_usage=true` | 转换结果没有 `stream_options` | Kimi、Qwen、Xiaomi、Zhipu 的 Responses → Chat 转换器 |
| `reasoning_content="first"` → `content="answer"` → `reasoning_content="second"` | 已发送 `output_item.done` 的 reasoning ID 又收到一次 delta | 四个 Chat → Responses 流转换器 |
| 未调用 `transform`，直接 `flush()` | 最后事件为 `response.completed` | 同上 |
| `function_call_output.output` 包含文本和 `input_image` | 整个数组被 JSON 字符串化，data URL 出现在工具文本中 | 四个 Responses → Chat 转换器 |
| Chat 工具消息包含文本和图片扩展块 | 只保留文本 | `openai/chat.ts`、`claude/chat.ts` |
| 智谱 Responses 请求携带 `reasoning.effort=high` | 转换结果没有 `reasoning_effort` | `zhipu/converter.ts` |
| 原生 Responses 已有正文 delta，但没有终态 usage | parser 返回全零 | `openai/usage.ts` |

范围限制：Kimi K3 已在 `src/routes/relay.ts` 的 `executeRelay` 中切换为原生 Responses；上表中 Kimi 的转换器问题主要影响仍经 Chat 适配的 K2 等模型，不应宣称 K3 也经过这些转换。

## 三、第一批：流式正确性与真实用量

### 1. 统一转换后请求的 usage 参数

上游依据：[New API #7389](https://github.com/QuantumNous/new-api/pull/7389)。

本地入口：`src/providers/{kimi,qwen,xiaomi,zhipu}/responses-relay.ts`。当前转换器采用字段白名单生成新对象，丢失输入中的 `stream_options`；对应的 `chat-relay.ts` 已在流式请求中合并 `include_usage: true`。

实施内容：

- [x] 在 Responses 转成 Chat 后，复用对应 Chat 请求归一化逻辑，合并 `stream_options.include_usage=true`，避免再维护一套互不一致的请求参数规则。
- [x] 保留合法的已有 stream options；拒绝把数组当配置对象。仅向支持该参数的 Chat 接口发送，原生 Responses 和 Messages 不注入 Chat 专用字段。
- [x] 保留当前“读取 finish_reason 之后独立 usage 块”的行为；不能因第二项流式结束优化而提前停止读取。
- [x] 核实实际请求是否经过该转换器：Xiaomi、Qwen、Zhipu 和 Kimi K2 适配路径纳入；Kimi K3、DeepSeek 原生 Responses 保持原路径。

验收：模拟上游只在 `include_usage=true` 时返回独立 usage 帧，确认客户端最终用量与 `recordUsage` 一致，缓存字段不丢失，仅记录一次。覆盖 Chat 直接入口、Responses 适配入口以及原生 Responses 的参数隔离。

### 2. 修复 Chat → Responses 的分段状态和结束原因

上游参考：[New API #7512](https://github.com/QuantumNous/new-api/pull/7512)。本地的 reasoning part added/done 事件已经存在，主要缺口是关闭后的状态复用和最终输出排序；空流成功问题是本次核查发现的关联缺口。

主要文件：`src/providers/{kimi,qwen,xiaomi,zhipu}/stream.ts`、`src/routes/relay.ts`。

实施内容：

- [x] 用有序输出项记录保存每个已关闭的 reasoning、message、tool 项；新分段分配新 ID 和递增 `output_index`，禁止向已关闭项写 delta。
- [x] 在 reasoning、正文和工具调用切换时关闭相应分段；`response.completed.output` 按实际输出次序组装，不能固定为“所有思考、所有正文、所有工具”。
- [x] 每个 item/part 的 added、delta、done 成对；保留已有 reasoning 回放标记和工具参数累积规则。
- [x] 给流转换器明确的结束上下文，区分正常结束、上游错误、传输中断和客户端取消。空流或未完成流不能无条件 `flush()` 成 `response.completed`。
- [x] 明确映射 `stop`、`tool_calls`、`length`、`content_filter` 等结束原因；`length` 形成 `response.incomplete` 并保留真实用量。仅在已完成的输出段后到来的合法新段可以继续，已经发出的整条 Responses 终态不得重新开启。
- [x] 路由层与转换器共同保证整条响应只有一个终态、只记账一次；已向客户端输出后不重新换号生成另一份答案。

验收：四个适配器共用一组参数化行为样例，覆盖思考→正文→思考、工具与正文交错、多个工具、正常结束后独立 usage、空流、突然 EOF、读取异常、客户端断开、显式错误、长度截断及重复 flush。对事件序号、项生命周期、最终 output 顺序、错误日志和记账次数做断言。

实施取舍：可以抽取必要的共享状态逻辑，但不把本轮扩大为所有 provider 的整体重写。供应商特有的 usage、模型名和 reasoning 回放处理继续保留。

## 四、第二批：多模态工具与智谱参数

### 3. 保留工具结果中的图片

上游依据：[New API #7510](https://github.com/QuantumNous/new-api/pull/7510)、[#7512](https://github.com/QuantumNous/new-api/pull/7512)。

本地证据：四个 Responses → Chat 转换器对非字符串 `function_call_output.output` 使用 `JSON.stringify`；OpenAI/Claude 的 Chat 转换器把工具 content 压成文本。Grok 已有工具图片提取与合并逻辑，可作为本地参考。

主要文件：`src/providers/{kimi,qwen,xiaomi,zhipu}/converter.ts`、`src/providers/openai/chat.ts`、`src/providers/claude/chat.ts`；参考 `src/providers/grok/relay.ts`。

实施内容：

- [x] 将受支持的结构化工具结果拆成文本和图片。Responses → Chat 的图片放在整批连续工具回复之后的 user 消息中，不能插入两个并行工具回复之间。
- [x] Chat → Responses 的工具图片按目标协议的图片输入表达；Chat → Claude 使用 Anthropic 支持的图片块或结构化 tool_result。同步处理同一转换路径中的普通 user 图片，避免只修工具图后仍丢用户图。
- [x] 保留 URL、data URL、detail 等目标协议支持的信息。不由网关下载、重新上传或转码图片；`file_id` 只在目标接口明确支持时保留。
- [x] 纯图片工具结果使用明确、短小的文本占位，保持 call ID 对应关系；普通字符串和业务 JSON 对象保持原有语义。
- [x] 先核实目标模型/接口的图片能力。对明确不支持或无法表达的媒体返回可解释的 4xx；不能静默丢图，也不能把 base64 当普通工具文本发送。
- [x] 仅修实际存在的转换方向。原生 Messages、原生 Responses、Sub2API 透传保留原始内容；不为对应 New API 的补丁新增本项目不存在的 Claude → Chat 通用入口。

验收：文本+图片、纯图片、两工具并行、末尾工具结果、URL/data URL、含未知块的数据、普通 JSON 工具输出以及不支持视觉的目标模型。捕获模拟上游请求，确认图片未落入工具文本、没有丢失或重复、工具回复仍连续、原输入对象未修改。覆盖 Grok 已有行为防回退。

### 4. 补智谱 Responses 推理强度映射

上游参考：[New API #7124](https://github.com/QuantumNous/new-api/pull/7124)。New API 修的是 Chat 请求字段遗漏；本地原生 Chat 已通过对象展开保留该字段，实际需修的是 Responses → Chat。

主要文件：`src/providers/zhipu/converter.ts`、对应转换测试及 relay 集成测试。

实施内容：

- [x] 核实智谱当前模型与接口支持的 effort 值，将 Responses 的 `reasoning.effort` 映射到 Chat 的 `reasoning_effort`。
- [x] 为兼容请求中的顶层 `reasoning_effort` 定义明确优先级：Responses 原生字段优先；若两者冲突，避免静默按另一个值计费。
- [x] 统一实际转发值与日志里的 `reasoningEffort`。不支持的值返回明确参数错误，不猜测 `max/xhigh/ultra` 等级等价关系。
- [x] 不把智谱规则扩散到所有国产模型；各供应商的推理参数分别遵循其接口契约。

验收：省略值、合法值、两字段一致/冲突、非法值、流式与缓冲客户端；同时确认原生 Chat、Messages 不因这项修改丢掉现有字段。

## 五、第三批：用量来源与模型目录

### 5. 先补缺失用量标识，估算扣费暂缓

上游参考：[New API #7427](https://github.com/QuantumNous/new-api/pull/7427)。上游使用预扣与结算流程；本地 `src/usage/recorder.ts` 是根据解析结果直接扣钱包或套餐，两者不能照搬。

已确认：`openai/usage.ts` 默认全零，仅在终态携带 usage 时更新；已有输出但断流时可能记录零费用。`UsageData` 和 `usage_logs` 当前也没有用量来源字段。另一方面，供应商显式返回全零完全可能是合法结果，不能用“是否大于零”判断是否收到 usage。

推荐先做：

- [x] 显式跟踪是否收到真实 usage、是否完整终态及中断原因；区分真实零用量、部分用量、缺失用量。
- [x] 给使用日志增加 `usage_source`（建议 `upstream/partial/missing/unknown`）；历史记录迁移为 `unknown`，不回填猜测来源。
- [x] 在详情/API 中展示来源及中断原因，前端对缺失用量作可见标记。已有真实或部分 usage 继续按现有规则结算，不能因为请求最终失败而抹掉已经获得的真实用量。
- [x] 保持终态、用量来源与业务状态独立：成功但缺 usage、失败但有 usage 都可以表达。

预计涉及 `src/providers/types.ts`、usage parsers、`src/routes/relay.ts`、`src/usage/recorder.ts`、`src/db/schema.ts`、新增迁移及日志 API/前端类型与展示。该批需独立数据库迁移和前后端兼容检查。

**本轮不默认启用估算扣费。** 当前 `src/routes/inputTokens.ts` 是预检用的粗略结构估算，会递归处理字符串，不适合直接计算图片、缓存和隐藏推理的收费 token。若后续需要估算结算，应单独确定开关与结算政策，至少具备：

- 真实 usage 始终优先；观察到的输出与终态快照去重。
- 区分上游明确失败、网络中断、客户端取消与空流；仅创建事件不能证明有可计费输出。
- 不把图片 base64、加密 reasoning 或工具 schema 的序列化长度直接当收费 token；不凭空补隐藏推理/缓存 token。
- 估算来源、算法版本、原始观察量与采用金额可审计，钱包、套餐、Key 配额、使用日志同一次结算。
- 默认关闭估算扣费；关闭时仍可观察缺失用量，不回溯修改历史账单。

## 八、实施结果（2026-09-26）

六项已完成，估算扣费仍未启用：

1. **主动获取流式用量**：四个 Responses → Chat 入口复用对应 Chat 归一化逻辑，保留合法 stream options 并启用 usage；账务直接解析原始 Chat 用量，读取结束原因之后的独立 usage 帧。Kimi K3 保持原生 Responses。
2. **流式状态**：四份近似重复的状态机合并为 `src/providers/chatResponsesStream.ts`，provider 包装层保留各自默认模型。按创建顺序保存输出项；思考、正文切段分配新 ID，工具参数可跨正文交错累积，等待真实 call ID，重复 flush 无输出。空流、中断、上游错误、客户端取消和长度/过滤终止得到相应终态。
3. **图片内容**：新增 `src/providers/toolMedia.ts`。工具图片在连续工具结果批次之后发送，Chat → Claude 使用原生图片块；保留原有字符串内容及业务 JSON。转换器支持 HTTP(S) 图片 URL 和 PNG/JPEG/WebP/GIF data URL；无法表达的文件句柄、音视频及混合未知工具块返回 400。仅对已核实不支持图片的 GLM-5.2 本地拒绝，其他型号的实际能力由上游继续校验；原生透传不受影响。
4. **智谱 effort**：GLM-5.3/5.3-Flash 接受 low/high/max，GLM-5.2 接受 high/max；省略时沿用上游默认。Responses 原生与兼容顶层字段冲突时返回 400，日志记录实际转发值。依据：[Z.ai 官方模型说明](https://github.com/zai-org/GLM-5/blob/main/README.md)。
5. **用量来源**：新增 `usage_source` 列及 `0014_usage_source.sql`，启动初始化也可幂等补列。新流量按协议证据标注 upstream/partial/missing，历史记录保留 unknown；终态没有 usage 时不会把此前的部分计数提升成完整用量。管理端详情和用户用量列表展示来源，保留既有扣费规则。未增加估算 token 或补收历史费用。
6. **Grok 4.7**：加入内置目录与明确价卡。每百万 token 的输入/缓存/输出价格为 2/0.5/6 美元；输入总量（含缓存与图片）超过 200,000 时为 4/1/12 美元。独立报告的图片输入 token 按相同输入档位计费；不加入未公开的 Fast 型号。数据库与文件自定义价格优先级保持，并支持显式关闭长上下文倍率。依据：[官方模型页](https://docs.x.ai/developers/models/grok-4.7)、[官方发布说明](https://docs.x.ai/developers/release-notes)。
