## 二、需要修复的问题（Bug Fixes）

### 1. OpenAI Responses 流式与缓冲模式的“空内容帧 + 流内错误”前置重试失效（P1）

- **上游依据**：[`c591412c4`](https://github.com/Wei-Shaw/sub2api/commit/c591412c42ab195dacdede9eb19f9cbfee221144)（PR #8305，`backend/internal/service/openai_gateway_passthrough.go`、`backend/internal/service/openai_capacity_shed_test.go`）
- **涉及本地文件**：
  - [`src/providers/openai/chat.ts`](../src/providers/openai/chat.ts)（`responsesStreamStartVerdict`、`inspectResponsesSseTerminalFailure`）
  - [`src/routes/relay.ts`](../src/routes/relay.ts)（流式 `peekSseStart` 与缓冲错误分类）
- **根因分析**：
  1. **流式路径空结构/空增量提前锁定响应**：
     `responsesStreamStartVerdict` 目前仅将 `response.created`、`response.in_progress`、`response.queued`、`response.metadata` 判为 `'continue'`。当上游先下发空结构帧（如空 `response.output_item.added`、`response.content_part.added`/`done`、`response.reasoning_summary_part.added`/`done`）或空字符串增量（如 `response.output_text.delta` 的 `delta: ""`、`response.output_text.done` 的 `text: ""`、`response.refusal.delta` 的 `delta: ""` 等），随后立即返回 `response.failed`（如 `server_is_overloaded`）或空 `response.completed` 时，`peekSseStart` 在收到首个空帧时即返回 `'pass'` 并向客户端刷出 HTTP 200 响应头，丧失了前置换号/同号重试能力。
  2. **流式路径未输出前收到可重试 `error` / `response.failed` 未触发重试**：
     在 `wantStream === true` 时，如果上游 HTTP 200 流在未产出任何有效内容前直接发送 `{"type":"error"}` 或 `{"type":"response.failed"}`（例如 `server_is_overloaded`、限流等），`responsesStreamStartVerdict` 当前返回 `'pass'`，直接把失败流写给下游而未进入重试循环。
  3. **缓冲模式（`openai-chat` 非流式）误判 `hasOutput`**：
     `inspectResponsesSseTerminalFailure` 遇到 `response.output_item.added`、`response.content_part.added` 或代码列举的文本、拒绝、函数参数、推理摘要增量事件时，无条件将 `hasOutput` 置为 `true`。当上游在 `response.failed` 之前先发了空 item/part/delta 时，`classifyBufferedResponsesFailure` 因 `terminal.hasOutput === true` 直接返回 `null`，导致非流式请求也无法故障转移。
- **修复建议**：
  - 抽取统一的“事件是否携带真实客户端输出”判定函数：
    - `response.output_item.added`：检查 `reasoning`（是否有 `encrypted_content` 或非空 `summary_text`）、`message`（是否有非空 `output_text` / `refusal`）、`function_call`（`arguments` 非空）、`custom_tool_call`（`input` 非空）、`compaction`（`encrypted_content` 非空）。
    - `response.content_part.added` / `response.content_part.done`：`output_text` 的 `text` 非空，或 `refusal` 的 `refusal` 非空。
    - `response.reasoning_summary_part.added` / `response.reasoning_summary_part.done`：`summary_text` 的 `text` 非空。
    - `response.output_text.delta`、`response.reasoning_summary_text.delta`、`response.reasoning_text.delta`、`response.function_call_arguments.delta`、`response.custom_tool_call_input.delta`、`response.refusal.delta`：`delta` 为非空字符串。
    - `response.output_text.done`、`response.reasoning_summary_text.done`、`response.reasoning_text.done`：`text` 为非空字符串；`response.refusal.done`：`refusal` 为非空字符串。
  - 仅跳过已识别事件中的明确空字符串或空结构。空白字符串、缺失或类型错误的增量字段、未知事件、加密推理、工具完成事件均保守视为不可重放边界；空参数的工具完成事件也不能重试。
  - `responsesStreamStartVerdict` 在未输出前遇到 `error` / `response.failed` 时保留原始错误事件，交由外层统一分类，不依赖后续事件或 EOF。硬错误原样返回，账号额度耗尽换号，请求级 overload 免罚并按提示等待。
  - `inspectResponsesSseTerminalFailure` 使用相同的输出边界判定；畸形 SSE 数据不能被忽略后误当空响应。`response.failed` 自带非空 output 时也保留原有保守处理。

### 2. Cloudflare 1010 / `browser_signature_banned`（HTTP 403）边缘拦截处理（P2）

- **上游依据**：[`e0fa4b94f`](https://github.com/Wei-Shaw/sub2api/commit/e0fa4b94f9b962949da039c09e63968358324e26)（PR #8255，`backend/internal/service/ratelimit_service.go`）
- **涉及本地文件**：
  - [`src/routes/relay.ts`](../src/routes/relay.ts)（`classifyUpstreamFailure`）
- **根因分析**：
  - Cloudflare 边缘拦截会返回 HTTP 403，格式可能是 HTML/纯文本（包含 `error code: 1010`），也可能是结构化 JSON（包含 `{"cloudflare_error": true, "code": 1010}` 或 `{"error_name": "browser_signature_banned"}`）。
  - 本地 `classifyUpstreamFailure` 对 HTTP 403 默认返回 `{ penalty: null, retryable: false }`：
    1. 因为 `retryable: false`，当池中存在多个账号（或不同代理出口）时，单次边缘拦截无法自动切换到其他账号重试；
    2. 若拦截响应体附带了包含 `RATE_LIMIT_MARKERS` 关键词的说明文本，还会误触发 `penalty: 'rate_limited'` 将正常账号冷却。
- **修复建议**：
  - 新增 `isCloudflareBotBlockResponse(text)` 辅助函数：有效 JSON 必须递归匹配节点中的 `cloudflare_error: true` + `code/error_code == 1010`，或 `error_name == "browser_signature_banned"`，支持大小写不敏感的键名及字符串代码；非 JSON 文本才使用 `error code: 1010` 匹配。有效 JSON 仅在 message 中提及 1010 不予豁免。
  - 在 `classifyUpstreamFailure` 处理 `response.status === 403` 时优先判断该条件，命中时返回 `{ penalty: null, retryable: true, accountScoped: true }`（允许换号重试，但不对该账号写入冷却惩罚）。
  - 本地普通 403 原本就不会自动惩罚账号；本次价值是避免关键词误冷却并允许换号。换号时清除当前粘性账号绑定，不将边缘拦截视为账号永久失效。

### 2. 补齐请求级 overload 的提示解析和实际重试等待（P1）

- **上游依据**：[`c591412c4`](https://github.com/Wei-Shaw/sub2api/commit/c591412c42ab195dacdede9eb19f9cbfee221144)（PR #8305，`backend/internal/service/openai_gateway_upstream_errors.go`）
- **涉及本地文件**：
  - [`src/routes/relay.ts`](../src/routes/relay.ts)（`parseRateLimitReset`、`parseBodyReset`）
- **现状对比**：
  - 本地 `parseRateLimitReset` 目前仅解析 HTTP 头 `retry-after`（秒或日期）、`x-ratelimit-reset-requests`、`x-ratelimit-reset-tokens` 以及响应体中的 `resets_at` / `resets_in_seconds` / `quotaResetDelay`。
  - OpenAI 在过载或限流时，可能通过 HTTP 头 `Retry-After-Ms`（毫秒）或 JSON 错误体内的 `error.headers['retry-after']`、`error.headers['retry-after-ms']`、`response.error.headers['retry-after']`、`response.error.headers['retry-after-ms']` 下发建议重试间隔。
- **更新建议**：
  - 在 `parseRateLimitReset` 中增加对 ` response.headers.get('retry-after-ms')` 的毫秒解析；
  - 在 `parseBodyReset` 中增加对 `error.headers`（及 `response.error.headers`）下 `retry-after` 与 `retry-after-ms` 的提取。
  - 仅扩展冷却时间解析不够：HTTP 503 overload 的旧分支固定冷却 30 秒；流式重试此前只有原因字符串，外层直接继续循环。新增独立 `retryDelayMs`，同时保留 HTTP 响应头和流内错误头，真正等待后再开始下一次请求。
  - 对明确的 OpenAI 请求级 overload，免除账号/模型冷却，允许当前账号再次参与选择；单次等待最多 8 秒，仍最多尝试 3 次。真实额度耗尽保留原有冷却与换号策略，不使用短等待替代账号限额。
  - 等待放在上一次尝试释放账号并发占位之后，并由请求的取消信号中断；不可重试错误和最后一次失败不等待、不新增尝试。
