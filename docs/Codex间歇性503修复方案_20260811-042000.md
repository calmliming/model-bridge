# Codex 间歇性 503 错误修复方案

## 问题现象

Codex 使用时出现循环性的 503 错误：
- 有时能正常使用
- 突然报 503 "no sub2api account configured"
- 等待一段时间（约 15 秒）后又能用
- 然后再次失败，不断循环

## 根本原因

**账户冷却机制导致的间歇性不可用**

当 sub2api 账户请求失败时：
1. Model-bridge 将该账户标记为"冷却中"（15 秒）
2. 在冷却期间，`pickAccount()` 函数找不到可用账户
3. 返回 503 错误："no sub2api account configured"
4. 15 秒后冷却结束，账户恢复，可以继续使用
5. 但如果上游仍有问题，会再次失败 → 再次冷却

**核心代码**（[src/routes/relay.ts:1458](src/routes/relay.ts#L1458)）：
```typescript
const cooldownUntil = relayToRelay 
  ? Date.now() + RELAY_TO_RELAY_COOLDOWN_MS  // 15秒冷却
  : failure.resetAt
await penalizeAccount(account.id, failure.penalty, cooldownUntil)
```

## 可能触发冷却的原因

### 1. 上游 Sub2API 服务不稳定
- Sub2API 服务偶尔超时或返回错误
- 网络连接不稳定
- Sub2API 的上游账户池耗尽

### 2. Sub2API 账户配置问题
- `proxyUrl` 配置错误
- API Key 无效或过期
- Sub2API 配额用尽

### 3. Sub2API 速率限制
- Sub2API 本身有速率限制
- 超过限制后返回 429 或 503 错误

### 4. 请求格式不兼容
- Model-bridge 发送的请求格式与 Sub2API 不完全兼容
- 特定的 model 参数不支持

## 诊断步骤

### 步骤 1：检查账户冷却状态

运行以下脚本查看账户实时状态：

```typescript
// 保存为 scripts/check-cooldown.ts
import { drizzle } from 'drizzle-orm/postgres-js'
import postgres from 'postgres'
import { config as loadDotenv } from 'dotenv'
import { accounts } from '../src/db/schema.js'
import { eq } from 'drizzle-orm'

loadDotenv()

const client = postgres(process.env.DATABASE_URL!)
const db = drizzle(client)

async function checkCooldown() {
  const sub2apiAccounts = await db
    .select()
    .from(accounts)
    .where(eq(accounts.provider, 'sub2api'))

  const now = Date.now()
  
  console.log('Sub2API 账户状态：\n')
  
  for (const account of sub2apiAccounts) {
    const isCooling = account.cooldownUntil && account.cooldownUntil > now
    const remainingSeconds = isCooling 
      ? Math.ceil((account.cooldownUntil! - now) / 1000) 
      : 0

    console.log(`账户: ${account.name}`)
    console.log(`  状态: ${account.status}`)
    console.log(`  代理URL: ${account.proxyUrl || '未设置'}`)
    
    if (isCooling) {
      console.log(`  ❌ 冷却中: 剩余 ${remainingSeconds} 秒`)
      console.log(`  冷却结束时间: ${new Date(account.cooldownUntil!).toLocaleString('zh-CN')}`)
    } else {
      console.log(`  ✓ 可用`)
    }
    
    if (account.lastUsedAt) {
      console.log(`  最后使用: ${new Date(account.lastUsedAt).toLocaleString('zh-CN')}`)
    }
    
    console.log()
  }

  await client.end()
}

// 持续监控模式
async function monitor() {
  console.clear()
  await checkCooldown()
  setTimeout(monitor, 2000) // 每2秒刷新
}

// 运行：npx tsx scripts/check-cooldown.ts
monitor().catch(console.error)
```

## 修复方案

### 方案 1：增加 Sub2API 账户数量（推荐）

**原理**：多个账户轮换使用，即使一个冷却也有其他可用

1. 在管理面板添加多个 sub2api 账户：
   - 可以是同一个 Sub2API 服务的不同 API Key
   - 或者不同的 Sub2API 服务

2. 每个账户使用相同的配置：
   - Provider: `sub2api`
   - Access Token: 不同的 API Key
   - Proxy URL: 相同或不同的服务地址
   - Weight: 10（平均分配）

**优点**：
- 可靠性高，一个账户冷却时自动切换到其他账户
- 不需要修改代码

**缺点**：
- 需要多个 Sub2API API Key
- 如果所有账户用的是同一个上游，并不能解决上游的问题

### 方案 2：调整冷却时间

**原理**：缩短冷却时间，减少等待

修改 [src/routes/relay.ts:110](src/routes/relay.ts#L110)：

```typescript
// 从 15 秒改为 5 秒
const RELAY_TO_RELAY_COOLDOWN_MS = 5_000
```

或者完全禁用冷却（不推荐）：

```typescript
const RELAY_TO_RELAY_COOLDOWN_MS = 0
```

**优点**：
- 快速恢复
- 适合临时性的网络问题

**缺点**：
- 如果上游真的有问题，会不断重试，浪费资源
- 可能触发上游的速率限制

### 方案 3：检查并修复 Sub2API 配置

#### 3.1 验证 proxyUrl

确保账户的 `proxyUrl` 正确：

```sql
-- 查询当前配置
SELECT name, proxy_url FROM accounts WHERE provider = 'sub2api';

-- 更新为正确的 URL（如果错误）
UPDATE accounts 
SET proxy_url = 'https://api.sub2api.com' 
WHERE provider = 'sub2api' AND name = 'your-account-name';
```

**常见错误**：
- ❌ `http://api.sub2api.com`（应该是 https）
- ❌ `https://api.sub2api.com/v1`（不要加 /v1 后缀）
- ❌ `https://www.sub2api.com`（可能不是 API 地址）

#### 3.2 验证 API Key

```bash
# 获取加密的 token（需要解密工具）
# 或在管理面板重新编辑账户，重新输入 API Key
```

#### 3.3 检查 Sub2API 配额

登录你的 Sub2API 控制台，检查：
- 账户余额是否充足
- 速率限制设置
- 是否有异常告警

### 方案 4：使用重试策略

修改代码增加智能重试（需要开发）：

在 `pickAccount` 函数中，当所有账户都在冷却时：
- 等待最快结束冷却的账户
- 或返回更友好的错误信息

## 立即可执行的修复步骤

### 如果你现在就要解决问题：

#### 快速方案 A：手动清除冷却

```sql
-- 直接清除所有 sub2api 账户的冷却状态
UPDATE accounts 
SET cooldown_until = NULL 
WHERE provider = 'sub2api';
```

或通过管理面板：
1. 进入"账户管理"
2. 编辑 sub2api 账户
3. 保存（会清除冷却状态）

#### 快速方案 B：修改代码禁用冷却

编辑 `src/routes/relay.ts`：

```typescript
// 第 110 行附近
const RELAY_TO_RELAY_COOLDOWN_MS = 0  // 改为 0
```

然后重启服务：
```bash
docker-compose restart model-bridge
```

#### 快速方案 C：添加第二个账户

1. 登录管理面板
2. 复制现有 sub2api 账户的配置
3. 创建第二个账户（可以用相同的 API Key 和 URL）
4. 这样即使一个冷却，另一个也能用

## 长期解决方案

### 1. 根治上游问题

如果问题在于 Sub2API 服务本身：
- 联系 Sub2API 服务提供商
- 检查网络连接质量
- 考虑更换更稳定的 Sub2API 服务

### 2. 改用直连 Provider

如果你有 Claude/OpenAI 等服务的直接账户：
- 添加这些账户到 model-bridge
- 配置 Codex 使用对应的端点
- 不再依赖 Sub2API

### 3. 实现智能降级

代码层面实现：
- 当 sub2api 不可用时，自动切换到其他 provider
- 或返回更友好的错误信息，告知用户等待时间
